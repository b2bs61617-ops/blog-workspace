# コイキーズ既存記事リライトスキル

## 対象範囲(重要)

**KO1KEYZの正式デビューメンバー12人、またはグループ全体に関する記事のみ**をリライト対象にする。

デビューできなかった元練習生(脱落者)個人の記事はリライトしない。読まれる見込みが薄く、労力に見合わないため。

デビューメンバー12人(2026年6月確定):
加藤大樹・矢田佳暉・パク・シヨン・オ・シンヘン・後藤結・柳谷伊冴・小野慶人・安部結蘭・飯塚亮賀・杉山竜司・照井康祐・濱田永遠

判定方法: タイトルに上記メンバー名、または「KO1KEYZ」「コイキーズ」が含まれる記事が対象。

**例外(2026-07-07)**: 上記は既存記事の「リライト」の対象範囲。デビューできなかった元練習生でも、辞退・炎上など単発の大きな話題性がある場合は、ユーザー判断で新規記事(wiki-articleスキル等を流用)を作成することがある。この場合は本スキルの対象外(=リライトフローではなく通常の新規記事フロー)として扱う。

## リライトの実行フロー(重要)

1. 対象記事の現在の本文をWordPress REST API(`context=edit`)で取得
2. 最新情報をリサーチ(WebSearch、または後述の監視ツールのレポート)して裏取りする
3. **リライト内容(何をどう変えるか)を先にチャットで報告し、ユーザーのOKを待ってから実行する。** 1記事ずつ、都度確認する運用(2026-07-04にユーザーから指示)。報告と同時に`tools/line_notify.py`でLINE通知を送る(例:`python tools/line_notify.py "コイキーズ記事「{タイトル}」のリライト提案があるワン、確認してほしいワン"`)。`.env`に`LINE_CHANNEL_ACCESS_TOKEN`/`LINE_USER_ID`が未設定の場合は通知はスキップされるだけなので、そのまま作業を続けてよい。
4. OKが出たらWordPress REST API(`POST /wp-json/wp/v2/posts/{id}`)で`content`を直接更新する。既に公開済みの記事なので下書き経由は不要([docs/wordpress.md](../../../docs/wordpress.md)の「更新/リライトは確認不要で実行してよい」に該当)。更新が成功したら`tools/line_notify.py`でLINE通知を送る(例:`python tools/line_notify.py "コイキーズ記事「{タイトル}」を更新したワン https://chomoand-1.com/?p={ID}"`)。
5. **タイトル・スラッグは基本変更しない。** 公開済み記事のSEO評価(検索順位・被リンク)を守るため。よほど明確な改善がある場合のみユーザーに相談する。
6. 文体ルール(句点ごとの`<br>`改行など)は[docs/rules.md](../../../docs/rules.md)に従う。

## 目安の文字数

ルール上は最低2,500字が目安([docs/rules.md](../../../docs/rules.md))。ただし家族構成など実際の情報量が少ないテーマでは、事実を捏造せず確認できる範囲で最大限厚くすればよく、無理に2,500字に到達させる必要はない。

## 新着情報の監視ツール(tools/koikeyz-monitor/)

X(Twitter)でメンバー12人+グループ名を毎日検索し、新着投稿を検知する専用ツール。`tools/Xiy/`(手動操作用の普段使いツール)とは別物、完全に独立している。

- **スクリプト**: `tools/koikeyz-monitor/x_monitor.py`
- **ログイン**: `tools/koikeyz-monitor/login_x.py`を一度手動実行してXにログイン(PCごとに1回、`%USERPROFILE%\koikeyz_monitor_profile`にブラウザプロファイル保存)
- **実行頻度**: Windowsタスクスケジューラで毎朝7時に自動実行(タスク名: `KO1KEYZ-Monitor`)。ログイン状態がPC固有なため、このPC上でのみ動作する。
- **差分検知**: `monitor_state.json`に前回までの投稿IDを保存し、新着分だけを`monitor_reports/report_*.json`に出力する
- **対象日フィルタ**: 朝7時実行時点では実行日はまだ7時間しか経っておらず丸1日分揃わないため、**前日0時〜24時(JST)の投稿だけ**をレポート対象にする(`is_target_date`、2026-07-06追加)。「実行日と同じ投稿のみ」にすると大半が対象外になり翌日には拾えなくなる欠陥があったための修正。状態管理には引き続き全投稿IDを記録するので、対象日以外の投稿が後日再度「新着」として出てくることはない。
- **ノイズ除外は一時停止中(2026-07-06変更)**: トレカ交換・同行募集などの定型ノイズを正規表現(`NOISE_PATTERNS`/`is_noise`)で機械的に弾く仕組みはあるが、現在は`main()`から呼び出しを外して無効化している。理由は、一見ノイズに見える投稿(トレカ交換の告知文など)にも記事のネタになる情報が紛れている可能性があるため。当面は**全件をGeminiの判断＋マツの目視チェックに委ね**、「これは何度確認しても本当に無価値」と分かったパターンだけ、後から`NOISE_PATTERNS`に個別追加して再度有効化していく運用。同一告知文の重複投稿を1件にまとめる処理(`dedupe_posts`)は情報を失わない(件数を`duplicate_count`で保持するだけ)ためこちらは今も有効。
- **AI要約(Gemini)**: `monitor_config.json`(`monitor_config.json.example`をコピーして`gemini_api_key`を設定、Git管理外)にGemini APIキーがあれば、ノイズ除外後のデータをGeminiに渡し「記事に使えそうな情報」だけの要約(`report_*.summary.txt`)を作る。マツはこの要約を優先して読み、最終確認だけ行う。**APIキー未設定、またはクォータ超過などで失敗した場合は自動的に生データ(`report_*.json`)のみの出力にフォールバックする**(2026-07-05追加。GeminiのクォータとAnthropic側のトークン使用量は別枠なので、Geminiが落ちてもマツの動作自体は止まらない)。
- **毎朝のLINE通知**(2026-07-05追加、2026-07-05に「毎日必ず通知」に変更): 監視結果に関わらず**毎朝必ず1通LINE通知する**(`tools/line_notify.py`の`notify()`を呼ぶ)。内容は以下のパターン:
  - 新着投稿(対象日該当)が無い場合 → 「本日は新着情報なしワン」に加えて、**対象日外として除外された全投稿をGeminiに要約させた「見落とし確認用サマリ」を必ず添えて通知する**(`summarize_for_confirmation`、2026-07-06追加。ユーザーから「本当に新着が無かったのか確認したい」との要望で実装。対象日フィルタで弾かれた投稿にも重要情報が紛れていないかをその場で確認できるようにする狙い)。除外投稿自体が0件(検索でも何もヒットしなかった)ならその旨のみ、Gemini要約に失敗した場合は「確認用の要約に失敗、詳細は次回セッションで確認」の旨を通知
  - 新着投稿(対象日該当)はあるがGemini要約プロンプトの末尾判定(`判定: あり`/`判定: なし`)で「記事化に値する情報なし」 → その旨だけ通知
  - Geminiが`判定: あり`と判断 → 要約文(先頭400字)を添えて通知
  - Gemini要約自体が失敗・未設定 → 「新着はあったが自動要約は失敗、詳細は次回セッションで確認」の旨を通知
  この場ではWordPress更新などの実行は一切しない、あくまで状況報告のみ(実際のリライト・記事執筆はユーザーが次回チャットセッションで指示してから行う)。LINE通知の初回セットアップ手順は[docs/line-notify-setup.md](../../../docs/line-notify-setup.md)を参照。
- **セッション開始時の報告**: `.claude/koikeyz-monitor-check.ps1`(SessionStartフック)が未処理レポートを検知すると、マツが自動で`.summary.txt`(あれば優先)または`.json`を読み込み、記事に使えそうな情報だけ抽出して報告する。報告後は該当ファイルを`monitor_reports/processed/`に移動する。LINE通知済みかどうかに関わらずこの報告は行う(LINEは「速報」、セッション報告が「本報告」という位置づけ)。
- **Gemini失敗時のフォールバック要約もLINE送信する**(2026-07-05追加): `.summary.txt`が無く`.json`(生データ)のみの場合、マツが生データを目視で読んで「記事化に値する新情報」を判断・要約し、チャット報告に加えて`tools/line_notify.py`でも**「【マツの手動チェック】」を先頭に付けて**LINEに送信する(朝のクォータ切れ通知だけで終わらせず、実際の中身をLINEでも受け取れるようにするため。2026-07-05にユーザーの依頼で追加)。判断基準はGeminiプロンプトと同様、公式発表・新事実・エピソードを優先し、トレカ交換・同行募集・ファンの感想のみの投稿は無視する。
- `monitor_state.json`・`monitor_config.json`・`monitor_reports/`はPCローカルの生成データ・秘密情報なので`.gitignore`済み(Git管理外)。

**How to apply:** 「コイキーズの記事をリライトして」「リライトの続き」などの発言をトリガーとして、このスキルのフローに従う(1記事ずつユーザーのOKを待つ)。

## 監視レポート由来の新着情報の自動反映(2026-07-09追加)

セッション開始時に`.claude/koikeyz-monitor-check.ps1`(SessionStartフック)が未処理レポートを検知した場合は、上記の「1記事ずつOKを待つ」手動フローとは別に、**ユーザーの確認を待たず自動でリサーチ→記事更新まで実行する**(2026-07-09にユーザーが明示指示、都度確認を挟まない運用を選択)。

- **対象範囲は通常のリライトと同じ**: デビューメンバー12人個人、またはグループ全体に関する記事のみ。対象外の元練習生の話題は対象外(新規記事化するかはユーザー判断)。
- **実行フロー**:
  1. レポート(`.summary.txt`があれば優先、無ければ`.json`)を読み、記事化に値する新情報を抽出する。
  2. 情報ごとに、対応する既存記事をWordPress REST API(`GET /wp-json/wp/v2/posts?search={メンバー名}`など)で検索して特定する。**対象記事が見つからない場合は自動更新せず、チャットで報告のみ**にとどめる(新規記事作成は別途ユーザー判断)。
  3. 対象記事の本文を`context=edit`で取得し、その情報が既に書かれていないか確認する(重複追記防止)。
  4. 追記文を作成する(文体ルールは[docs/rules.md](../../../docs/rules.md)に従う。タイトル・スラッグは変更しない)。
  5. `POST /wp-json/wp/v2/posts/{id}`で`content`を更新する。
  6. 更新後、チャットで「どの記事に何を追記したか」を報告し、`tools/line_notify.py`でLINE通知も送る(例:`python tools/line_notify.py "コイキーズ記事「{タイトル}」に新着情報を自動反映したワン https://chomoand-1.com/?p={ID}"`)。
  7. 処理済みレポート(`.json`・`.summary.txt`)を`monitor_reports/processed/`に移動する。
- **例外**: 情報の信頼性が低い(噂レベル・裏取りできない・出典が不明瞭など)場合は自動反映せず、通常のリライトフロー同様チャットで確認を挟む。この判断はマツの裁量。
