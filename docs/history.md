## 複数セッション同時実行時のコミット混入(2026-07-09)

複数セッションが同時に動いていると、`git add`直後に別セッションの`commit`が割り込み、無関係な変更同士が1つのコミットに混ざることがあると判明した。

**現在のルール(CLAUDE.mdにも記載):** `git add`の後は`git commit`前に必ず`git status`で意図したファイルだけがステージされているか確認する。見覚えのない変更が混ざっていたら一旦止めてユーザーに報告する。すでにコミットされてしまっていても、中身が両方とも正当な変更なら実害はないことが多いので、無理に`reset`で分離しようとせず状況を説明するだけでよい。

## ラヴ上等2「1人4記事」を1人1記事に統合(2026-07-27)

上記の重複調査で「恋リア転換後85記事のうち77記事が2,500字未満(サイトの品質ルール未達)、うち76記事がラヴ上等2カテゴリに集中」と判明。原因は1人の出演者を「wikiプロフィール/学歴/職業年収/逮捕歴」の4記事に細切れにした結果、1記事あたり700〜1,400字しか書くことがなかったこと。`site:chomoand.com`で見てもこのジャンルの記事はほぼインデックスすらされていなかった。

- **方針**: トモキの承認を得て、14人分(きぃちゃん・つーちゃん・Baby・あも・Milk・おとさん・二世・てんてん・てかりん・タックル・ヤンボー・緋咲一馬・るる・尾田優也)の4記事を1本の総合wikiプロフィール記事(2,500字以上)に統合。統合先はwikiプロフィール記事のIDをそのまま使い(URL温存)、残り3記事はdraft化(削除はしない)。
- **やり方**: きぃちゃん1人分を手作業で統合して型(プロフィール表→番組説明→経歴→学歴→職業/年収→犯罪歴→SNS→まとめボックスの順、SWELLブロックのHTML書式を踏襲)を作り、`articles/lovejoto_kiichan_merged.html`として保存。残り13人分は4グループに分けてAgentサブエージェントに並行委任し、同じ型で統合・WordPress反映まで実施(新事実の捏造は禁止、ソース記事にある事実のみを使い、文章のつなぎと番組説明の導入文のみ加筆可、というルールを徹底)。
- **結果**: 91記事(公開85・下書き6)→ 公開25・下書き66に整理。2,500字未満の公開記事は77本→1本(番組メンバー一覧のハブ記事、別枠のため今回は対象外)まで削減。重複タイトルはゼロ。統合後HTMLは`articles/lovejoto*_merged.html`(14ファイル)としてリポジトリに保存済み。
- **Why**: 「10記事書いても順位が付かない」という相談がきっかけ。実態は85記事あったが、うち大半が薄すぎる・一部は重複していたことが根本原因だった可能性が高い。ジャンル選び(恋リアwiki型)自体の失敗と判断する前に、まず自分たちの実行の粗さを疑うべきだった。
- **How to apply**: 「1人=複数記事」戦略([koi-realスキル](../.claude/skills/koi-real/SKILL.md)参照)は、KO1KEYZのように**各記事が独立して2,500字を超えられるだけの情報量がある場合のみ**有効。出演者発表直後で情報が少ない段階から機械的に4分割すると、今回のような薄い記事の量産になる。情報が少ないうちは1本の総合プロフィール記事で公開し、放送が進んで書けることが増えてから学歴記事・カップル記事などを独立させる、の順番を守ること。

## SNS拡散調査→X自動投稿ツール実装→Pay-Per-Use判明で手動投稿に方針転換(2026-08-09〜08-10)

ブログ記事のSNS拡散を強化する一連の作業の記録。

1. **競合のSNS拡散手法を実地調査**: KO1KEYZ・恋リア系の競合ブログのX投稿を`Xiy`で収集・分析。fstopics.com(`@renaifreaks`)は同じ記事タイトルを数日連続で再投稿する「連投型」、teiban-navi.comは「歴代〇〇一覧」のような網羅的保存版記事が何年も他ユーザーに自然リンクされ続ける「資産型」という、2つの異なる拡散スタイルが判明(収集データは`tools/Xiy/posts_sns_promo_*/`参照)。
2. **プラットフォーム横断でインプレッションの伸ばし方を調査**: X(本文にURLがあるとリーチ30〜50%減)、Instagram(カルーセル・冒頭3秒のフック型)、TikTok(視聴完了率重視)、YouTube(サムネ・タイトルの情報の出し分け)の一般的な最新知見をWebSearchで収集。
3. **Xの自動投稿ツールを実装**: `tools/x_auto_post.py`を新規作成。Zapierの標準連携はリプライスレッドが組めず本文にURLを含める形しか作れなかったため、X API v2を直叩きして「1件目=画像+フック文(URL無し)→2件目=1件目へのリプライでURLのみ」の2連投を自前実装。`publish`スキルに組み込み、記事タイプ別のフック文・ハッシュタグの型も整理した(詳細は[docs/x-auto-post-setup.md](x-auto-post-setup.md))。
4. **Developer App作成中にX APIの料金体系が別物になっていたと判明**: 2026年2月にFree/Basic/Proの月額プランが廃止されPay-Per-Use(従量課金)一択になっており、単価は通常投稿$0.015・**URL付き投稿$0.20**(2026-04-20改定、通常の約13倍)。無料クレジットも表示上$0.00で、即座に無料で試せる状態ではなかった。
5. **ユーザー判断で方針転換**: 月100投稿規模でも$10〜20程度で致命的な金額ではなかったが、「まずは手動投稿で慣れてから、自動化は他のSNSから着手する」という判断になった。3サイトとも`.env`に`X_*`キーは設定せず、`tools/x_auto_post.py`はコードとして残しつつ休眠状態にした。`publish`スキルは代わりに手動投稿用のフック文・ハッシュタグ案を提示する運用に変更。
6. **手動投稿の operational な学び**: Xの「返信」と「引用する」は別機能で、URLを2件目に置く際は必ず**返信(リプライ)**を使うこと(引用は新しい独立投稿になり、それ自体がURL付き投稿としてリーチが落ちるため意味がなくなる)。実際にKO1KEYZブログの記事([TOWA(濱田永遠)の家族構成](https://chomoand-1.com/what-is-the-family-compositio-11059))で手動投稿の型を確認済み。

**Why**: SNS拡散を強化したいという要望から出発したが、実装を進める過程でX API自体の商用条件が大きく変わっていた(調査時点の一般知識と現在の実態にズレがあった)ことが分かった。技術実装よりも前提条件の確認が先に必要なケースの実例。

**How to apply**: 次にX自動投稿を再開する場合は、まず[docs/x-auto-post-setup.md](x-auto-post-setup.md)の最新の「現在の状態」を確認してから着手する(料金体系はさらに変わっている可能性がある)。次の自動化ターゲットはInstagram(現状Jetpack Socialで単一画像のみ、カルーセル対応が次の検討課題)。TikTok・YouTubeは動画制作インフラ自体が無く、着手する場合は別途新規インフラの検討から必要。

chomoand-1.com記事ID11093(TOWAのジェラピケ記事)で、ユーザーがスクリーンショットで「黒い丸で囲った線」を指摘。調査したところ、リード文(冒頭段落)の直後に`---`を書くと`blog-upload`スキルのSTEP1/1.5で`<!-- wp:separator --><hr class="wp-block-separator ..."/><!-- /wp:separator -->`に変換され、SWELLテーマの`.post_content hr`スタイル(`border-bottom:1px solid rgba(0,0,0,.1);margin:2.5em 0`)で薄い横線として表示される仕様だったと判明。どのスキルにも明記されていない慣習で、過去セッションが自然に書いていた見た目のクセだった。

- **恒久対応**: [docs/rules.md](rules.md)の記事構成スタイル節と[.claude/skills/blog-upload/SKILL.md](../.claude/skills/blog-upload/SKILL.md)のSTEP1に「リード文直後に`---`を書かない」ルールを追記(commit acfdb11)。
- **既存下書きへの遡及対応(部分実施)**: ユーザーから「下書きを全て消して」という指示があったが、文脈から記事削除ではなく「この区切り線だけ削除」の意図と判明(誤読しかけたため一度立ち止まって確認、詳細は[[feedback_ambiguous_delete_scope]]相当の教訓)。chomoand-1.comの下書き34件のうち**1ページ目(更新日時が新しい順の先頭20件)のみ対応し、リード文直後に区切り線があった11件からWordPress REST API経由で除去済み**(ID: 11088, 11093, 11096, 11122, 11125, 11132, 11136, 11138, 11139, 11192, 11194)。残り9件は元々この区切り線が入っていなかったため対応不要。
- **未対応**: chomoand-1.comの**2ページ目以降の下書き(古い順、14件)**、および**chomoand.com・chomoand-0.comの下書き**(このPCには`.env`のWP_TREND_*/WP_AUDITION_*未設定で確認不可)にはこの遡及対応をまだ行っていない。

**Why**: 同じ区切り線問題が他の下書き・他サイトにも残っている可能性があるため、次に関連する相談が来たときに「もう直したはず」と思い込んで見落とさないよう記録する。

**How to apply**: KO1KEYZ記事や区切り線の見た目について再度相談が来たら、まず上記の対応済みID一覧と未対応範囲(2ページ目以降・他2サイト)を確認し、必要なら同じ手順(`content.raw`を取得→リード文直後の`wp:separator`ブロックだけを正規表現で検出・除去→REST APIでPOST更新)で続きを行う。
