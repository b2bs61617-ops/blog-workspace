# 記事作成の基本ルール

## 記事作成方針(最重要)

トレンドブログの記事は「人の疑問に答える」ことを最優先に書く。人は何かを検索するとき必ず「疑問」を持って検索している。その疑問に正面から答える記事こそが価値を持ち、検索流入につながる。

- タイトルは疑問形・または疑問に答える形にする(例:「〇〇とは?」「〇〇の理由を解説」「〇〇はどうなった?」)
- **タイトルは最大35文字までに収める**(2026-08-03にユーザー指示、当初45文字だったが同日中に35文字へ再指示・上書き)。検索結果での見切れを防ぐため、記事タイトルを決めたら文字数を数えて確認する。
- **タイトルの一番最後はなるべく「?」か「!」で締める**(2026-08-12にユーザー指示。例:「吉澤閑也の誕生日会場はどこ?GLAMSと判明!」)。文字数(35文字以内)の都合や文脈的に不自然になる場合は無理に付けなくてよい。
- **タイトル中の「?」「!」は全角(「？」「！」)を使う**(2026-08-20にユーザー指示。「タイトルの記号は大文字がいいな 約束」)。半角(`?`/`!`)だと日本語タイトルの中で文字が小さく見切れて見えるため、日本語タイトル(chomoand.com・chomoand-0.com・chomoand-1.com JP版)では常に全角を使う。**韓国語版・英語版のタイトルは対象外**(ハングル・アルファベットの文中では半角`?`/`!`が自然なため、KR/EN版は従来通り半角のままでよい)。アイキャッチ画像(`--top`/`--bottom`)のテキストも同じ理由でタイトルと同じ全角記号に揃える。この指示が出た時点の既存記事(公開済み・下書き問わず)の一括修正は対象外、今後新規に作るタイトルから適用する。
- **アクセサリー・私服など「私物特定」系記事のタイトルには、着用場所・シーン(番組名・会場名・共演者との集まりなど)を入れて絞り込む**(2026-08-20にユーザー指示)。「〇〇のピアスは?」のような書き方だと本人の全ピアス記事のようにざっくりしすぎるため、「マツダスタジアムで〇〇が付けていたピアスのブランドは?」のように、いつ・どこで身につけていたものかが分かる形にする。撮影場所が非公開の場合は「〇〇との2ショットで」のように共演者・シーンで代用してよい。
  - **グループ間の交流・コラボが絡む題材では、元ネタ投稿に付いているファン発のクロスオーバー呼称(ハッシュタグ)がSEO的に強い場合がある**(2026-08-20、千賀健永×宮近海斗の帽子記事で追加指示。元ツイートのハッシュタグ「#いつもココロに千ちゅーぶ」「#キストラ」を見た上で「この辺のハッシュタグは使えない?」と提案があった)。「キストラ」(Kis-My-Ft2×Travis Japanのファン間呼称)のように、2グループの絡みを指す定着した通称がある場合、事実確認([WebSearchなどで実際に使われている呼称か裏取り必須])できたら`【】`でタイトル先頭に入れると、個人名だけの検索者と呼称で検索するファンの両方を拾える。呼称の由来が不確かなまま憶測で使わない。
  - **私物の持ち主が1人だけの記事で共演者名も入れる場合、「AとBの〇〇」という書き方だと2人の共有物のように読めてしまう**(2026-08-20、上記記事で「千賀健永と宮近海斗の帽子は、だと千賀も被ってるような言い回しじゃない?」と指摘)。「Bがかぶってた〇〇」「Bが着けていた〇〇」のように、私物の持ち主(B)を主語にした一節で所有を明確にし、共演者名(A)は文字数が厳しければタイトルから削って本文・キストラ等の呼称タグ側に譲ってもよい。実例:「【キストラ】千賀健永と宮近海斗の帽子は?」→「【キストラ】宮近海斗がかぶってた帽子は?」に修正。
  - **「私服」はあくまで服(トップス・ボトムスなど)を指す言葉なので、ネックレス・ピアス・ブレスレットなど服以外のアクセサリー記事のタイトルで「私服〇〇」と書くと服なのかアクセサリーなのか一瞬迷う**(2026-08-20、松田元太のディズニーネックレス記事で「ディズニー私服ネックレスだと、服なの?ネックレスなの?って思う」と指摘)。アクセサリー単体の記事では「私服」の代わりに「着用」を使う(例:「ディズニー私服ネックレスは?」→「ディズニー着用ネックレスは?」)。Tシャツ・カーディガンなど衣類そのものの記事では「私服Tシャツ」のように「私服」のままでよい(私服+衣類名は同じ「服」のカテゴリ内なので曖昧にならない)。
  - **複数メンバー・複数アイテムが並行して記事化されるとき(同じ日にまとめて下書きを作るときなど)、既存記事群の命名パターン(このメンバーは既に`【〇〇】`表記を使っているか等)を確認してから統一する**(2026-08-20、松田元太のディズニー私服Tシャツ・ネックレスの2記事が`【松田元太】`表記なしで作られ、後から既存記事(post 812)に揃えて修正した)。新規記事を作る前に同じメンバー・同じサイトの既存タイトル(WP REST APIで`search`検索、またはdocs記事一覧)をざっと見て、命名規則が浮いていないか確認する。
  - **KO1KEYZ関連のタイトルで「SEOを考慮して」と明示的に指示された場合、グループ名は英語表記「KO1KEYZ」だけでなくカタカナ表記「コイキーズ」も検討する**(2026-08-25、「ケミ名」まとめ記事のタイトルで確認)。既存記事群は基本的に`KO1KEYZ`表記で統一されているが、日本語で検索するファンは「コイキーズ」で検索することも多い。1本のタイトルに両方を詰め込む必要はなく、その記事の主要キーワード(ユーザー指定があればそれを優先)に応じてどちらか自然な方を使う。**アイキャッチ画像の`--main`(中央の大きいロゴ風テキスト)は引き続き常に`KO1KEYZ`(英語表記)で統一する**(サイト全体のブランディングの一貫性のため、タイトル表記がカタカナでもアイキャッチのグループ名は変えない)。
- 記事の冒頭でその疑問に端的に答える(結論ファースト)
- 本文は疑問の答えを深掘りする構成にする
- 情報の羅列ではなく、読者の疑問を解消することを意識する

## 記事構成スタイル(2026-08-04にユーザー指示、chomoand-0.com/chomoand-1.com共通)

chomoand-1.com(コイキーズブログ)の照井康祐のぬいぐるみ記事(https://chomoand-1.com/what-is-the-brand-of-kosuke-te-11004)が「すごく見やすい」とユーザーから評価され、この書き方をchomoand-0.com(ジャニオタブログ)にも展開する指示があった。以降、新規記事・リライトともに以下の構成をベースラインにする。

- 冒頭はcapboxでまとめず、プレーンな段落2〜3文で「フック→太字での結論(価格・事実を`<strong>`でインライン)→本文で扱う内容の予告」の流れにする。
- **記事中に`---`(区切り線/`<hr>`)を一切使わない**(2026-08-12にリード文直後だけ禁止、2026-08-18に全セクション間へ禁止範囲を拡大・ユーザー指示で確定)。`---`はSTEP1で`<hr>`に変換され、STEP1.5でGutenbergの`wp:separator`ブロックになり、SWELLテーマの`.post_content hr`スタイル(`border-bottom:1px solid rgba(0,0,0,.1);margin:2.5em 0`)で薄い横線として表示される。当初は「リード文の直後だけ」不要と指摘されていたが、2026-08-18のKO1KEYZファンミFCブース記事(chomoand-1.com記事ID11468)で「各セクションの下にあるこれ、なくせる?」→「これは全記事書く際必ずの約束で」と明言され、**H2セクションの合間も含め記事中のどこにも`<hr>`を置かない**のが確定ルールになった。見出し(`<h2>`)そのものがセクションの区切りとして十分機能するため、追加の区切り線は不要という考え方。**2026-08-16追記・2026-08-18更新**: 執筆時の記憶に頼る注意書きだけでは別セッションで再発するため、[blog-upload/SKILL.mdのSTEP1.5](../.claude/skills/blog-upload/SKILL.md)側で記事中の`<hr>`をすべて機械的に除去する処理に変更済み。この段落の注意書きは執筆時点で最初から書かないための努力目標として残すが、実際の防止策は変換処理側にある。
- 単発の事実(商品情報・動画情報など)は表にせず地の文で説明する。`<table>`は複数選択肢の比較・スペック比較など本当に表形式が向く内容だけに使う。
- 画像はページ上部に総合ヒーローとして置くのではなく、その画像を話題にしているセクションの近くに配置する。
- 関連記事リンクは記事末尾に`<ul>`でまとめるだけでなく、本文中の自然な文脈でも関連記事へインラインリンクを貼る。
- **出典figcaptionのCSS値はサイトごとの既存の慣例に従う(サイト間で使い回さない)**。chomoand-1.com(KO1KEYZ系記事)は`style="text-align:center;font-size:12px;"`が多数派。chomoand-0.com側は既存記事の慣例(`font-size:0.8em;color:#888;`など)をそれぞれ踏襲する。どちらのサイトで作業するときも、先に`articles/`配下の同サイトの既存記事をgrepして現在の主流スタイルを確認してから合わせる。
- **同じ記事内で段落の結び文句を使い回さない**(例:「〜と言えそうです」を4段落連続で使うなど)。AI生成っぽく見える一因になるので、文末表現(「〜でした」「〜そうです」「〜考えられます」「〜ところです」等)を段落ごとに意識して変える。指示・命令口調に近い硬い言い回し(「〜という点には留意してください」等)も、二文に分けるなどして柔らかく言い換える。

Why: capbox多用・表の使い過ぎ・トップに無関係な画像を置くといった構成の"重さ"が読みにくさの主因だと複数回指摘があり、chomoand-1.comの照井記事で改善版が「見やすい」と評価された。2026-08-04にこの改善構成をchomoand-0.comにも展開する方針が確定した。

How to apply: chomoand-0.com・chomoand-1.comどちらの記事を書く/リライトするときも、このセクションの構成ルールをデフォルトとして使う。個別記事の細かい調整は都度ユーザーの指示に従う。

## 「パッとわかる」要約ボックスの型(2026-08-06にユーザー指示、ロケ地・グルメ特定系記事の新ベースライン)

Travis Japan「JUST!シン日本遺産」宮城編のロケ地・食べ物特定記事(chomoand-0.com、`articles/travis_japan_shinnihonisan_sendai_aobamatsuri.md`)で試行錯誤の末に固まった構成を、ユーザーから「とても見やすい、これを基準にしたい」と明示的に評価された。以降、同種の記事(ロケ地特定・グルメ特定など複数トピックを扱う記事)ではこの型をベースラインにする。

- **記事冒頭の並び順は「番組情報capbox」→「この記事でわかることbox」の順**(逆順で試したところユーザー指示で入れ替えた)。
- 「この記事でわかること」boxは、他のcapboxと差別化するため**タイトル部分を紺色(`background:#1a3c4c`)の帯+白文字**にし、中身は`swell-block-capbox`ではなく通常の`<div>`(chomoand-0.comの`wp:html`内capbox無枠バグ回避のためインラインstyle)。
  ```html
  <div style="border:1px solid #ddd;border-radius:4px;margin:0 0 16px 0;overflow:hidden;">
  <p style="font-weight:bold;font-size:1.05em;margin:0;padding:10px 18px;background:#1a3c4c;color:#fff;">この記事でわかること</p>
  <ul style="margin:0;padding:14px 18px 14px 34px;background:#f7f7f7;">
  <li>ロケ地</li>
  <li>対決企画</li>
  <li>飲食したもの</li>
  </ul>
  </div>
  ```
  - **中身は項目名(ラベル)だけの簡潔な箇条書きに留める**(詳細な内容は書かない)。詳細は各項目名だけ書き、具体的な答え(仙台城跡・ずんだ等)は書かない。当初は各項目に具体的な答えまで詰め込んだが「もう少し簡単でもいいかも」とユーザーから簡略化の指示があった。色分け(項目ごとに文字色を変える)も試したが「色は変えなくていい」と却下された。プレーンな黒文字でよい。
- **各H2セクションの見出し直後にも、そのセクション専用の簡易ボックスを置く**。タイトルバーなしの軽量版(`border-left`アクセントのみ)で、「ロケ地:」「食べたもの:」など2〜3行のラベル+具体的な内容をそのセクションの一番最初に簡潔に入れる。
  ```html
  <div style="border:1px solid #ddd;border-left:4px solid #1a3c4c;border-radius:4px;padding:10px 16px;margin:0 0 16px 0;background:#f7f7f7;">
  <p style="margin:0;"><strong>ロケ地:</strong>仙台城跡</p>
  <p style="margin:4px 0 0 0;"><strong>食べたもの:</strong>ずんだ団子・ずんだシェイク・仙台ずんだサイダー</p>
  </div>
  ```
  トップの要約boxが「見出しだけの目次」、各セクション冒頭のミニboxが「その節の答えを先出し」という役割分担になる。
- **まとめ(`## まとめ`)の最後に、ファン目線の一言コメントを添える**(例:「この放送をきっかけに、仙台城跡や青葉まつりを実際に訪れる聖地巡礼も楽しそうですね!」「2人と同じようにずんだ甘味や屋台グルメを味わってみるのも、ファンならではの楽しみ方と言えそうです。」)。事実の羅列だけで終わらせず、読者が実際に真似したくなるような呼びかけで締める。
  - **このファン目線コメント(および補足の一文)は、チェックリストのタイトルバー付きboxの中には入れず、boxの外の通常の段落(`<p>`)として書く**(2026-08-20、KO1KEYZ振り付け担当記事で確定)。box内は`&#10003;`の箇条書き(結論の要点)だけに留め、感想・呼びかけ文はboxを閉じた直後に別の`<p>`ブロックとして追加する。
  - Why: 最初box内の箇条書きの下に感想文を追記したところ、「コメントは枠外にしたい」「(補足の一文も)これも枠外に」と2段階で指摘があった。boxは「事実の要点だけを機械的に示す場所」、感想文は「地の文としての結び」という役割分担がユーザーの意図。
  - How to apply: まとめboxを書くときは、box内は`&#10003;`の箇条書きだけで閉じ、ファン目線の感想・呼びかけ文(「〜できそうですね!」「〜が待ち遠しいですね!」等)はbox閉じタグの直後に独立した`<p>`として追加する。
- **まとめの箇条書き内でメンバー名を並べるときは、本文中でニックネーム(「しずや」等)を使っていても、まとめでは他メンバーと表記を揃えて名字(「吉澤」)にする**。まとめは一覧性が最優先のため、愛称よりも統一感を優先する。

Why: 番組情報→要約boxの順序、要約boxのタイトルバー化、各セクション冒頭のミニボックス、まとめ末尾のファン目線コメント、まとめでの名字統一——これらはすべて実際にユーザーと複数回やり取りしながら固まった型で、最終的に「とても見やすい!ブログの書き方これ基準にしたい」と明示的な太鼓判をもらった(2026-08-06)。

How to apply: ロケ地特定・グルメ特定・複数の出来事を時系列で扱う記事など「パッとわかる要約」が読者の助けになる記事では、このボックス構成をデフォルトの型として使う。単純なプロフィール記事など要約の必要性が薄い記事では無理に使わなくてよい。

### 複数人物を紹介するセクションは1人ずつ個別の枠で囲む(2026-08-17追加)

作詞家・作曲家・スタッフなど複数人を同じ見出し配下で紹介する記事で、地の文の段落を人物ごとにただ並べただけだと誰が誰の説明か視覚的に分かりにくい、とユーザーから指摘があった(KO1KEYZデビューシングルの作詞クレジット記事)。

- 人物ごとに`<div style="border:1px solid {BORDER};border-radius:4px;padding:14px 18px;margin:0 0 16px 0;">`で個別に囲み、先頭に`<p style="font-weight:bold;font-size:1.05em;margin:0 0 8px 0;color:{ACCENT};">{人物名}</p>`を置いてから説明文を続ける(KO1KEYZ記事のACCENT色は`#8a8378`)。背景色は付けず枠線のみで十分(囲みが並ぶと背景色まで付けるとくどくなる)。
- Why: 「ひとりひとり線で良いから囲ってほしい」という指示。地の文の段落だけでは人物の切れ目が弱く、太字の名前だけでは目立たない。
- **personbox内の説明文には、本名・生年月日・出身地など基本スペックを必ず入れる**(2026-08-20、KO1KEYZ振り付け担当記事で「スペック忘れずに」と再指摘)。経歴・実績のエピソードだけで終わらせず、プロフィール表がない人物紹介セクションでは、personboxの説明文の中に基本スペック(分かる範囲で本名・生年月日・出身地など)を必ず含める。
- How to apply: 「〇〇はどんな人?」「関係者紹介」のように複数人物を列挙するセクションでは、最初からこの個別枠(通称personbox)を使う。1人しか出てこないセクションでは不要。personboxを書くときは、経歴エピソードだけでなく基本スペックも忘れずに1文目あたりに入れる。

## 記事投稿時のセット項目

タイトル・本文・アイキャッチ画像・スラッグをセットで作成・投稿する。

- スラッグはタイトルをアルファベット(ローマ字 or 英訳)に変換して設定する(例:「下妻市長 自殺 理由」→ `shimotsuma-mayor-suicide-reason`)。デフォルトのスラッグは日本語になってしまうため、WordPress REST APIの`slug`フィールドに必ず英字スラッグを含める。
- 手順の詳細は[blog-uploadスキル](../.claude/skills/blog-upload/SKILL.md)を参照。

### 完了報告に含める項目(2026-07-19にユーザー指示)

記事を作成したら、ファイルに埋め込む必要はなく、**ユーザーへの完了報告(チャット)で**タイトル・想定検索キーワード・記事構成(見出し一覧)の3点を伝える。

## 記事の質(濃く・詳しく書く)

薄い記事は価値が低い。1記事あたりの情報量を最大化する。

- 文字数は最低でも2,500字以上を目指す(理想は3,500〜5,000字)
- 各H3セクションに十分な説明・エピソード・補足情報を入れる
- 「不明」「確認できていません」だけで終わらせず、周辺情報・推察・SNSの声・関連エピソードを膨らませる([sns-researchスキル](../.claude/skills/sns-research/SKILL.md)で情報を掘る)
- プロフィール表に続いて「性格」「好きなもの」「エピソード」なども積極的に加える
- 経歴は1行にまとめず、各ステップに背景・結果・視聴者の反応を添える
- SWELLブロック(capbox・マーカー・インデントボックス・ボーダーリスト)をフル活用する
- 学校・番組・グループには「どんな〇〇か?」補足ブロックを必ず入れる

## 地図埋め込み(必須ルール)

学校・出身地・職場・観光地・店舗など、**場所が特定できていれば必ずGoogleマップを埋め込む**。「わかっていれば必ず」がルール。

```html
<iframe
  src="https://maps.google.com/maps?q=場所名&t=&z=14&ie=UTF8&iwloc=&output=embed"
```

## 画像埋め込みルール(必ずXの画像を使う・2026-07-27にユーザー指示)

**ブログ記事で画像を使う際は必ずX(Twitter)の投稿画像を使う。** Instagramなど他のSNSや無関係な画像を代わりに使わない。手順:

### 例外: 公式YouTube動画が元ネタの場合は動画から直接フレームを切り出す(2026-08-03にユーザー指示)

話題の元になっている場面が**公式YouTube動画に映っている**場合、Xの特定投稿のスクリーンショットをそのまま埋め込むのではなく、**動画から直接その場面のフレームを切り出して使う**(手順は[docs/tools.md「記事本文用に動画から1コマだけ手動で切り出したい場合」](tools.md)参照)。X投稿はブランド特定などの調査の参考にとどめ、画像の実体は一次ソース(公式動画)から取得する。

- Why: 川島如恵留のピアス記事で、Xユーザーの特定投稿に埋め込まれた動画スクリーンショットをそのまま使っていたところ、「じぇらさんの投稿の引用ではなく、公式YouTube本編からTシャツ/場面がわかる画像を直接使ってほしい」とユーザーから指示があった。他人の投稿を模倣・引用したような見え方を避けたい意図。
- How to apply: 元ネタが公式YouTube動画であることが分かっている記事では、先に動画から直接フレームを取得できないか検討し、可能ならそちらを優先する。X投稿の画像をそのまま使うのは、公式動画が存在しない/特定できない場合(ブランド公式の商品写真との比較画像など、動画由来ではないもの)に限る。

1. 元ツイートから画像URLを取得する(取得方法は下記「Xの投稿を軽く1件だけ調べたい場合」参照)。
2. 画像をダウンロードし、`POST {サイトURL}/wp-json/wp/v2/media`でWordPressのメディアライブラリにアップロードする。
3. アップロード後にWordPressが自動生成する`medium`/`large`などのサイズURL(`media_details.sizes`)を使う。**オリジナルの巨大画像(`full`)をそのまま`width`/`height`固定で埋め込むと、記事本文エリアの幅からはみ出して見切れる。**
4. 埋め込みは以下の型を使う(`large`サイズを基準にsrcsetで縮小版も指定し、`style="max-width:100%;height:auto;"`でレスポンシブにする):
   ```html
   <figure class="wp-block-image size-large">
     <img src="{large画像URL}" alt="説明" width="{large幅}" height="{large高さ}"
       style="max-width:100%;height:auto;"
       srcset="{medium画像URL} {medium幅}w, {large画像URL} {large幅}w, {full画像URL} {full幅}w"
       sizes="(max-width: 1024px) 100vw, 1024px">
     <figcaption>出典:{投稿URL}</figcaption>
   </figure>
   ```
5. **画像の下に必ず`<figcaption>`で出典(投稿URL)を明記する。** ユーザーから出典URLの指定がない場合は、記事に使う前に必ず確認する。
   - **投稿者の表示名・XアカウントID(@〜)はどちらも本文・figcaptionに書かない**(2026-07-18にユーザー指示)。figcaptionはURLのみでよい。本文中で個別のXユーザーの投稿を紹介する際も「〇〇さんの投稿」のように名前を出さず、「Xでの投稿では」「Xでは、こんな声も」のような書き方にする。
   - **一般人(ファン・非公式アカウント)の投稿本文をそのまま引用ボックスに入れない(2026-08-22にユーザー指示)**。「投稿日:」「投稿内容:」のようなミニボックスで元ツイートの文言をそのまま「」で切り出して載せたところ、「一般人の投稿だからこれはいらない」と指摘された(Travis Japanの直筆サイン記事、chomoand-0.com記事ID886)。投稿内容は地の文で要約・言い換えて説明すれば十分で、本人の言葉遣いをそのまま切り出して目立たせる必要はない。公式アカウント・企業アカウントの発表文言を引用する場合はこの限りではない(一般人のプライバシー配慮が目的のルールのため)。
   - **地の文に言い換えていても、元ツイートの文の順番・構成をそのまま1文ずつなぞる要約は「投稿そのまま感」が出るためNG(2026-08-23にユーザー指摘)**。推し活グッズ交換レート記事(chomoand-1.com記事ID11722)で、「〜という質問が寄せられました」「これに対して回答者は〜と前置きしつつも、〜と答えていました」「あわせて〜とも述べています」のように元ツイートの展開を逐文追いする書き方をしたところ、「Xでの投稿そのまま感が強い」と指摘された。単語を言い換えるだけでなく、要点を1〜2文に要約・統合し、記事の地の文としての語り口(「〜という場面がありました」「〜という声も添えられていました」のように出来事として一段引いて紹介する)に変える。

## Xの投稿を軽く1件だけ調べたい場合

`x.com`のツイートURLはWebFetchで直接取得しようとすると402エラーになりやすい。1件のツイートのテキスト・投稿者名・投稿日時・画像URル(原寸)だけサクッと知りたい場合は、Xiyツールを起動しなくても`https://api.fxtwitter.com/{ユーザー名}/status/{ID}`をWebFetchすれば取得できる。画像は`https://pbs.twimg.com/media/xxxxx.jpg?name=orig`の形で原寸URLが返る。複数投稿をまとめて深掘りする調査には引き続き[sns-researchスキル](../.claude/skills/sns-research/SKILL.md)のXiyツールを使う。

## 本文中の強調・ボックス装飾ルール(2026-08-11追加)

結論・重要な数字など、本文中で目立たせたい箇所を強調する際のルール。

- **強調はSWELLの「マーカー」機能(`<span class="swl-marker mark_◯◯">`)を使う。** `border-bottom`など独自CSSでの下線は使わない(宮近海斗のカルティエ腕時計記事で最初`border-bottom`のインラインstyleを使ったところ、ユーザーから「線これじゃない、色付きのやつ」と指摘され、SWELL標準のマーカーに差し替えて解決した)。基本形は`<strong><span class="swl-marker mark_◯◯">テキスト</span></strong>`(`<p>`内、`wp:paragraph`のままでよく`wp:html`で囲む必要はない。マーカーはCSSのみで動作するため、`swell-block-capbox`のようなJS依存のブロックとは違い`wp:html`内でも問題なく表示される)。

## ✔チェックリストの枠線は`has-border -border02`クラスに頼らずインラインstyleで組む(2026-08-12判明)

`<p class="has-border -border02 wp-block-paragraph">`(✔箇条書きのまとめ・注意点リストで多用しているクラスの組み合わせ、サイト全体で100件以上の既存記事が使用)は、SWELL本体のCSS上は`.has-border.-border02{border:var(--border02)}`(`--border02: double 4px var(--color_main)`)として定義されており理論上は青い二重線が表示されるはずだが、実際にはswell-block-capboxの`cap_box_content`内にネストした場合などに枠線が表示されないケースが確認された(chomoand-1.comのKCON LA配信記事、まとめcapbox内の✔リストでユーザーから「見やすく枠で囲って」と指摘があり判明)。

- **確実に枠線を表示させたい場合は、クラス指定ではなくインラインstyleで直接ボーダーを組む。** 例:
  ```html
  <div style="border:2px solid var(--color_main, #2456e0);border-radius:8px;background:rgba(36,86,224,0.06);padding:1em 1.25em;">
  <p style="margin:0;">
    ✔ 項目1<br>
    ✔ 項目2
  </p>
  </div>
  ```
  (`<!-- wp:html -->`で囲むこと。`var(--color_main, #2456e0)`のようにフォールバック値を必ず添えておくと、テーマ側の変数が読めない環境でも色が消えない。)
- 上記の「関連記事の内部リンクが3件以上並ぶ文章」の箱スタイル(このすぐ上のセクション)も同じ理由(クラス依存だと表示が不安定)でインラインstyle化されたもの。✔チェックリストも同じ考え方で統一する。
- How to apply: 新規記事・リライトを問わず、✔で始まる箇条書きを目立たせたい箇所(まとめboxの要点・視聴方法の注意点など)を書くときは、最初から`has-border -border02`を使わずこのインラインstyleパターンを使う。既存記事にこのクラスが残っている場合、次にその記事を触る機会があれば同様に直しておくとよい(能動的に全件一括修正するタスクではない)。
- How to apply: Travis Japanメンバー個人の記事(1人が主役の単独記事)で本文強調・構造box(概要box・要約box・ミニbox・特徴box)・関連記事ボックス・まとめボックスを作るときは、上記マーカー色表とパステル配色をそのメンバーの色で統一する。複数メンバーが均等に登場するグループ記事では引き続き紺(`#1a3c4c`)のデフォルト配色でよい。他グループ(KO1KEYZなど)の記事でメンバーカラーを絡めた強調をしたい場合も同じ考え方(マーカー色を公式カラーに一番近いものへ寄せる)を援用してよい。

## 絵文字について

WordPress記事本文で絵文字(🔵❤️💚など)がうまく表示されない場合がある。色や項目を表す際は絵文字ではなく、文字(色名・太字・括弧書きなど)で表現する。

## メンバー名の英語表記ルール(KO1KEYZ)

12人の名前を一覧表にする際(絵文字・カラーまとめなど)は「英語表記(現地語表記)」の形にする(2026-07-14にユーザー指示)。

- 韓国籍メンバー(パク・シヨン、オ・シンヘン。漢字表記が無い): 「SIYOUNG(パク・シヨン)」のように英語表記(カタカナ)

## UIボックスのアクセントカラーはメンバーカラーと被らせない(KO1KEYZ、2026-08-11追加)

capbox・タイトルバー・border-leftなど記事の構造的な装飾(内容とは無関係な「この記事でわかること」ボックスなど)に使う色は、KO1KEYZ12人の公式メンバーカラー(赤・オレンジ・黄色・黄緑・緑・水色・青・群青・紫・ピンク・白・ブラウン。[docs/eyecatch-style.md]や`articles/ko1keyz_lapone_boys_membercolor_matome.html`参照)と紛らわしくない色を選ぶ。

- 紺(`#1a3c4c`、他サイト共通のデフォルト)は青・群青系メンバーカラーと混同されうるため、KO1KEYZ記事では避ける。
- クリーム色系も白(シヨン)・ブラウン(オ・シンヘン)と近く紛らわしいため避ける。
- **無難なのは彩度を抑えたウォームグレー**(実例: `#8a8378`)。白文字とのコントラストも保ちやすい。
- Why: 部屋割り予想記事(私物の色がメンバー特定の根拠になっている内容)で、UIの装飾色がメンバーカラーと紛らわしいとユーザーから複数回指摘された(紺→濃いグレー→クリーム案→ウォームグレーの順で調整)。
- How to apply: KO1KEYZ記事で新しくボックス系装飾の配色を決めるときは、まずメンバーカラー一覧と照合し、被らない彩度低めの色(グレー系統がベター)を選ぶ。

### サービス開始・アプリ導入系記事の「手順」はタイトルバー付きboxの番号リストにする(KO1KEYZ、2026-08-19追加)

KO1KEYZ Chat(プラチャ)開始告知記事で、「始め方」を`<p>`内の「1. 〜<br>2. 〜<br>3. 〜」という素のテキスト箇条書きにしていたところ、「ここは枠とか使って見やすく」とユーザーから指摘があった。

- 手順・ステップものは、[「この記事でわかること」box](#パッとわかる要約ボックスの型2026-08-06にユーザー指示ロケ地グルメ特定系記事の新ベースライン)と同じ「タイトルバー+リスト」の型を流用する。KO1KEYZ記事のタイトルバー色は上記のウォームグレー(`#8a8378`)を使う。
  ```html
  <div style="border:1px solid #ddd9d3;border-radius:4px;margin:0 0 16px 0;overflow:hidden;">
  <p style="font-weight:bold;font-size:1.05em;margin:0;padding:10px 18px;background:#8a8378;color:#fff;">◯◯の始め方</p>
  <ol style="margin:0;padding:14px 18px 14px 34px;background:#f7f6f4;">
  <li style="margin:0 0 8px 0;">手順1</li>
  <li style="margin:0 0 8px 0;">手順2</li>
  <li style="margin:0;">手順3</li>
  </ol>
  </div>
  ```
  (`<ol>`を使うことでリスト自体に番号が振られるため、本文側で「1.」「2.」と手打ちする必要はない。`<!-- wp:html -->`で囲むこと。)
- Why/How to apply: アプリのインストール手順・購入手順・応募手順など「手順もの」を書くときは、最初からこの番号リストboxを使う。他サイト(chomoand-0.com等)で手順ものを書く場合も同じ考え方(その記事のアクセントカラーでタイトルバー化)を流用してよい。

## ランキング・比較表を含む記事の配色統一ルール(chomoand-0.com、2026-08-13追加)

複数グループの数字を比較するランキング記事(例: 旧ジャニーズFC会員数ランキング記事)で、box装飾・表のヘッダーの配色についてユーザーから複数回の追加指示があり固まった型。特定メンバーのカラーに寄せる指定がない、グループ横断・複数項目比較の記事に適用する。

- デフォルトの紺(`#1a3c4c`)ではなく、**淡いパステルブルーで記事内の全boxの枠色を統一する**(2026-08-13、旧ジャニーズFC会員数ランキング記事でユーザー指示)。「この記事でわかること」box・各セクション冒頭のミニbox・まとめの箇条書きboxまで、記事内のすべての構造boxを同じ配色で揃える。
  - 実例配色: タイトルバー/表ヘッダー背景`#6a8caf`(白文字)、ボーダー`#cddbe9`、背景`#eef3f8`。
- **単独の比較表(`wp:table`)のヘッダー行も、box装飾と同じ配色に合わせる。** ヘッダー行だけ紺など別の色のまま残すと、box群との統一感が崩れる。
- **ランキング表で1〜3位がある場合は、金・銀・銅をイメージした淡い色でその行だけ強調してよい**(実例: 1位`#fff6db`、2位`#f4f4f4`、3位`#fbe9dd`、順位セルの文字色もそれぞれの縁取り色に合わせて強調)。4位以降は白と薄いグレーの縞々(ゼブラストライプ)にすると読みやすい。
- Why: 会員数ランキング記事で、最初は表にだけ金銀銅の色をつけたところ「枠にも統一して色味欲しい」「パステル・淡い色で」と追加指示があり、記事内の全boxと表ヘッダーを同一のパステル配色に揃える形で決着した。
- How to apply: 複数グループ・複数項目を比較するランキング/比較表形式の記事(chomoand-0.comの一般記事)では、最初からこの配色パターンを使う。Travis Japan個人記事・KO1KEYZ個人記事のようにメンバーカラーが指定されるケースは、引き続きそちらのカラー指定ルールを優先する。
- **セクションごとにパステルboxを置く構成にした場合、H2セクションの間の`<hr>`(wp:separator)は入れない**(2026-08-19、同記事でユーザー指示「各項目のこの下線なくして」)。box自体が視覚的な区切りとして機能するため、hrまで重ねると線が過剰になる。box装飾がなく通常の`<p>`だけが並ぶ記事では、従来通りH2セクション間に`<hr>`を入れてよい。

## 美容アイテム・ナイトルーティン特定記事のルール(KO1KEYZ、2026-08-11追加)

KEITO・SIYOUNGの「ナイトルーティンで判明」型記事(公式YouTube動画+Xの気づき投稿から使用美容アイテムを特定する記事)を2本続けて書く中で固まった、この種の記事専用の追加ルール。

- **価格まとめcapboxのすぐ下に「購入先」capboxを必ず置く**。各アイテムごとに公式オンラインショップ(例: `themedicube.jp`)や公式Qoo10/楽天ショップへのリンクを1行ずつ入れる(2列capbox、`is-style-small_ttl`でよい)。
- **メンバー個人の単独記事(wiki・愛用品特定など)では、タイトル・見出し・地の文で本人呼称にローマ字の公式ステージネーム(例: SIYOUNG・KEITO)を使う**。本名(パク・シヨンなど)は初出のプロフィールセクション見出し・プロフィール表でカッコ書きするだけに留める(例: `SIYOUNG(パク・シヨン)`)。既存の[メンバー名の英語表記ルール](#メンバー名の英語表記ルールko1keyz)は複数人の一覧表向けだが、この「本文全体でローマ字表記を主にする」方針は個人記事にも適用する(2026-08-11、ユーザー指示で全面的にローマ字化)。
- **本文中の装飾ボックス(流れ紹介box・関連記事box等)の色は、対象メンバーの確定メンバーカラー([[reference-blog-workspace]]の`ko1keyz-no-color`記事参照)に寄せたパステルにする**。Travis Japan記事向けの配色ルール(上記「本文中の強調・ボックス装飾ルール」)と同じ考え方をKO1KEYZ個人記事にも適用する。カラーが「白」など背景に馴染んで見えにくい色の場合は、そのまま白にせず、パール/シルバー寄りの薄いグレーブルー(例: `border:1px solid #dde3e8;border-left:4px solid #a9b6c2;background:#f5f7f9;`)で代用する。
- **「SNSでの反応」セクションは、複数の独立した反応が集まっている場合のみ作る。きっかけになった投稿1件しか無い場合はセクション自体を作らない**(2026-08-11、ユーザー指示で削除)。「1人だけの個人的な声だから」が理由で、[SNSの反応まとめセクションの見せ方](#snsの反応まとめセクションの見せ方2026-08-03にユーザー指示)のカテゴリ分けcapbox構成は複数の声が集まったときだけ使う。
- アイキャッチは通常どおり[KO1KEYZアイキャッチ生成ツール](tools.md#ko1keyzアイキャッチ生成toolseyecatch_koikeyzpy)(Canva MCPが使えない場合のフォールバック)で作り、記事の`featured_media`に設定する。動画から切り出した本文用フレーム画像をそのままアイキャッチ代わりに使い回さない。

Why: KEITO記事(2026-08-10)を土台にSIYOUNG記事(2026-08-11)を書く過程で、購入先リンク・ローマ字表記・メンバーカラーに寄せた配色・SNS反応セクションの要不要について複数回ユーザーから直接の追加指示があった。次にKO1KEYZの別メンバーで同種の記事を書くときに毎回同じ指示を受けずに済むよう、確定した型としてここに残す。

How to apply: KO1KEYZメンバー個人の「使用アイテム特定」「ナイトルーティン」系記事を新規に書く/更新するときは、このセクションを[YouTube動画発記事の情報の選び方](#youtube動画発記事の情報の選び方2026-07-30にユーザー指示最重要)と合わせてチェックリストとして使う。

## 表(テーブル)のスタイルルール(2026-08-03にユーザー指示、既存ルールと統合)

記事内で「表が見づらい」という指摘が来たら、表の種類によって対応が異なる。

- **単独の比較表・一覧表(コーデまとめ表など)**: [blog-uploadスキルSTEP1.5](../.claude/skills/blog-upload/SKILL.md)に既に詳細ルールあり。`<!-- wp:html -->`のCustom HTMLブロックに埋もれさせず、`<!-- wp:table -->`のコアブロックとして`<figure class="wp-block-table"><table class="has-fixed-layout"><tbody>...</tbody></table></figure>`の形にする。既存の公開記事(chomoand-0.com ID184)で実証済みの形式で、SWELL側の`.wp-block-table`用CSSが効いて列幅が均等に割り付けられる。
- **capbox内の2列表(項目名:値の商品情報表・動画情報表など)**: `swell-block-capbox`のdiv自体がSWELL独自装飾のため`<!-- wp:html -->`で囲む方針は変わらないが、中の`<table>`は罫線・背景色が一切当たらず素のまま表示されることがある。この場合は`<table style="border-collapse:collapse;width:100%;">`とし、各`<td>`に`style="border:1px solid #ccc;padding:8px 12px;"`を直接指定する(項目名側の列は`background:#f0f0f0`などで塗って値の列と区別する)。`wp:table`ブロックに変換すると`swell-block-capbox`の外枠デザインが崩れるため、capbox内はこのインラインstyle方式が現状の最適解。
- How to apply: 記事に表を入れるときは、独立した一覧表かcapbox内の情報表かをまず見分け、上記どちらの形式かを使い分ける。
- **記事冒頭の「基本情報まとめ」表はcapbox形式を優先する**(2026-08-06確定)。曲名・撮影場所・撮影日など項目:値形式の概要表を記事の導入直後に置く場合、`wp:table`の素の表よりも「タイトルバー付きcapbox+インラインstyleの表」の方が見やすいとユーザーから評価された(Travis Japan「On My Road -Stadium ver.-」ロケ地特定記事で、`wp:table`表を後からcapbox形式に変更)。他サイト(KO1KEYZ記事など)の「◯◯とはどんなグループ?」系表も同じ考え方で統一してよい。

## ロケ地・撮影日のファクトチェック技法(2026-08-06追加)

ロケ地や撮影日をSNS情報から特定・裏付けする記事を書く際に有効だった調査手法。

- **公共施設・会場が絡む場合は、その施設の公式サイトの「利用予定表・行事予定表(月間カレンダー)」を確認する**。スタジアム・ホール・公園などは月ごとのPDF/ページで「一般利用可」「養生期間」「大会名」などを公開していることが多く、特定の日が本当に外部の撮影に使える状態だったか(逆に大会・工事で使えなかったか)を裏付けられる。Travis JapanのMV撮影日特定では、エコパスタジアム公式サイトの月間予定表で「6月15日〜10月31日は大会準備のため使用不可」と判明し、SNS投稿者が示唆していた時期(7月)を否定し、6月上旬に絞り込めた。
- **台風・天候がらみの裏話は、気象庁・都道府県の公式防災ページや地元テレビ局の天気記事で日付を裏取りできる**(例:「◯◯県 災害警戒本部 設置期間」で検索すると、警戒本部の設置・解散日時から接近日を特定しやすい)。
- **SNS投稿(特にX)が別のSNS(Instagramストーリーズなど)のスクリーンショット・転載である場合、投稿者本人ではなく元の投稿者が誰かを見極める**。投稿文面(「いつもお世話になってる◯◯さん」等)やリンク先(`instagram.com/stories/...`)から元アカウントを辿り、可能であれば動画・作品本編のスタッフクレジット(エンドロール)と突き合わせて本人特定の裏を取る。
- **本編クレジットに実名が載っている制作スタッフ(監督・プロデューサーなど)は、記事中で実名を出してよい**(2026-08-06確認)。[画像埋め込みルール](#画像埋め込みルール必ずxの画像を使う2026-07-27にユーザー指示)にある「Xユーザーの表示名・アカウントIDを本文に書かない」ルールは、一般ファンのプライバシー保護が目的であり、公式クレジットで既に名前が公開されている制作側の人物(監督・プロデューサー等)には適用しない。ただし出典元(Instagramストーリーズなど)は明記し、本人の投稿を無断転載しているような書き方は避ける。
- **MVなど映像作品のロケ地・撮影日を調べるときは、制作スタッフ(VFX・美術・撮影部など)がポートフォリオ用に投稿する「制作クレジット」投稿もチェックする**(2026-08-17追加)。監督・プロデューサーだけでなく2D VFX・AI映像などの担当者名、撮影日(複数日ロケの場合は日付ごとのスタッフ配置まで)が詳細に載っていることがある。X上でこの投稿への言及・引用リポストが見つかったら、Instagram側の元投稿もXiyで直接開いて全文を取得する(Instagramの投稿URL単体をXiyに渡せば取得可能)。上記の「本編クレジットの実名は出してよい」ルールがそのまま適用できる。
  - **この種の投稿はVFX(グリーンバック合成・AI生成背景など)のBefore/After比較画像を伴うことが多く、「ロケ地で実際に撮れた場面」と「後から合成で足された場面」を区別する重要な手がかりになる**。ロケ地特定記事で複数カットの一致点を並べる際は、この裏取りをせずに「MV全体がそのロケ地で撮影された」と一括りにすると不正確になりうる。人物単体のカット(バス車内など)はグリーンバック合成の可能性を疑い、複数人が同時に写り立ち位置・影の向きが自然に揃っているカット(集団ダンスシーンなど)を実写ロケ判定の主な根拠にする。
  - Why: KO1KEYZ「KO1WORLD」ロケ地特定記事(chomoand-1.com下書きID11410)で、ユーザーから制作クレジット投稿のURLを渡され、VFXスタッフ(bookiee・kisaki・Jeonghoon Yeom)の実名と撮影日(2026年7月13〜15日)が判明した。Before/After画像を見ると、バス車窓の景色やバスの外装ロゴはAIで合成されたもので、実際にロケ地で撮れていたのは複数人が写るダンスシーンだけだったと分かった。

## 文体ルール

- 句点(。)で文が終わったら必ず`<br>`で改行を入れる。
  ```html
  <p>文章A。<br>
  文章B。<br>
  文章C。</p>
  ```
  記事HTML生成時・文書作成時すべてに適用する。既存記事の修正時も同様。
- **まとめの結びに、テーマにまだ詳しくない読者へ向けた行動喚起の一文を添えるのは効果的**(2026-08-06、ユーザー指示で追加し好評)。例:「これまで◯◯にあまり縁がなかったという方も、これをきっかけに一度△△してみてはいかがでしょうか!」。この手の呼びかけ文は句点「。」ではなく**感嘆符「!」で締めてよい**(ユーザー明示指示。通常の文体ルールは「。」+`<br>`だが、呼びかけ・誘い文句は熱量を出すため「!」を使う)。
- **「調査の結果、〜ことが分かりました」のような硬い言い回しは避け、「徹底的に調べてみたところ」「気になって調べてみたら」のようなフランクな言い回しにする**(2026-08-12にユーザー指示)。このブログは調査会社やニュース記事ではなく、あくまでファンが自分で調べて記事を書いている体裁が望ましい。同じ記事内で同じ言い回しを繰り返すと機械的に見えるため、上記のように毎回少し表現を変える([同じ記事内で段落の結び文句を使い回さない](#記事構成スタイル2026-08-04にユーザー指示chomoand-0comchomoand-1com共通)の考え方と同じ)。
  - Why: 吉澤閑也の誕生日会場特定記事で「調査の結果」という書き出しが「固い」と指摘され、「あくまでファンが調べて記事書いてるかんじ」にしたいという明確な意図が示された。
  - How to apply: 「調査の結果」「調査したところ」のような硬い言い回しを書きそうになったら、「気になって調べてみたら」「実際に調べてみると」「詳しく見てみたところ」などファン目線の言い回しに置き換える。結論を断定する文体そのもの(「〜と分かりました」「〜と判明しました」)は変えなくてよく、あくまで書き出しの硬さだけを和らげる。

## ファッション・私物特定記事のルール(2026-07-29にユーザー指示)

芸能人の着用アイテム(帽子・メガネ・服・時計など)のブランドを特定する記事を書く際の注意点。

- **私物と断定しない**。動画・写真に写っているだけでは、本人の私物なのかスタイリストが用意した衣装なのかは分からない。「私物とみられる」「私物使い」のような断定的な表現は避け、確証がない場合は「この帽子が本人の私物なのか、スタイリストが用意したものなのかは明言されておらず不明」のように留意点として明記する。
  - Why: ユーザーから「私服かどうかは不明」と指摘があり修正した。私服・私物という前提で書くと誤情報になりかねない。
  - How to apply: 着用アイテムを紹介する記事全般(ブランド特定・コーデ紹介系)で、私物/私服という言葉を使う前に根拠(本人のSNS投稿など)があるか確認する。根拠がなければ断定を避ける。
  - **例外(2026-08-07、七五三掛龍也のSamba LT特定記事で指摘)**: 同じアイテムがMV・歌番組など複数の公式コンテンツにまたがって登場している場合は、「私物かスタイリスト用意か不明」という留意点の一文自体を書かなくてよい。ユーザーいわく「MVと歌番組で履いてるから、スタイリストが用意したんだろうなってファンもわかってると思う」とのことで、複数の公式露出がある時点で読者にはスタイリスト用意である見当がついており、あえて明記すると冗長になる。単発の1カットのみで確認されたアイテムの場合は、引き続き従来通りこの留意点を書く。
- **元ネタのSNS投稿(画像・キャプション)を参考にはしても、その投稿を模倣・パクったような書き方にしない**(2026-08-03にユーザー指示)。投稿のキャプション文言(例:「私物 靴下 ファミマ(¥594)」のような短いラベル書き)をそのまま言い換えただけの記述で終わらせず、番組・放送回の特定、価格相場の比較、ブランド側の公式発表(コラボの発売日・型番など)といった**投稿単体には書かれていない裏取り情報**を必ず加えて記事の付加価値にする。画像を記事に埋め込む場合も[画像埋め込みルール](#画像埋め込みルール必ずxの画像を使う2026-07-27にユーザー指示)通り出典URLのみ明記し、投稿者本人の言葉づかいをなぞらない。
  - Why: 松田元太の私服特定記事で、参考にした投稿の内容をなぞるだけで終わらないよう書き方に注意してほしいとユーザーから指示があった。
  - How to apply: 執筆前に「この文はSNS投稿のキャプションを言い換えただけになっていないか」を確認する。価格・購入先などの事実は出典として引用してよいが、地の文は自分たちで調べた裏付け情報(番組名・放送日・公式価格・型番・過去の類似アイテムとの比較など)を主軸に組み立てる。
  - **具体例(2026-08-03、宮近海斗のsacai私服記事で再度指摘あり)**: 「話題の投稿では現在の入手価格として20,900円が紹介されていました」「(投稿では20,900円で紹介)」のように**元投稿を主語にして価格を紹介する言い回しは避ける**。代わりに「発売当初の価格は42,900円(税込)でしたが、発売から2年以上が経った現在は、セールや古着・リユースショップなどを通じて2万円前後まで値下がりして流通していることもあるようです」のように、**投稿を出典として名指しせず一般的な相場情報として書く**。一覧表の価格欄も同様に「定価42,900円(投稿では20,900円で紹介)」ではなく「定価42,900円(現在は古着・リユースショップで2万円前後も)」の形にする。
- **同じ動画・企画を扱う既存記事とテンプレ的な言い回しを使い回さない**。特に同じ動画に複数メンバーが映っている場合、メンバーごとに複数記事を書くことがあるが、「〇〇らしいアイテム選びと言えそうです」「〇〇のファッションセンスの一端がうかがえる」のような結び文句や、導入の「Travis Japanの公式YouTubeチャンネルで公開された『〜』に出演した〇〇が着用している〜が話題になっています」という書き出しパターンをそのまま使い回すと、コピペした記事に見えてしまう。
  - Why: 中村海人のニット帽記事が、先に書いた宮近海斗のメガネ記事・釣り堀ファッション記事と表現が似すぎていて「コピペと思われちゃう」とユーザーから指摘された。
  - How to apply: 新しい記事を書く前に、同じ動画・企画を扱った既存記事(`articles/`配下)があれば読み、書き出し・ロゴ/アイテムの解説文・締めの一文の言い回しを意識的に変える。同じ構成(結論→動画紹介→特徴→ブランド解説→まとめ)は使ってよいが、文の言葉選び・切り口は記事ごとに変える。
- **価格・販売元も可能な限り調べて載せる**。ブランド名だけで終わらせず、公式サイト・END.やStockXなど海外リセールサイトを調べ、素材・発売時期・価格・取扱店をスペック表(`<table>`)にまとめる。海外ドル価格しか確認できない場合も、「340ドル(目安で約5万1,000円)」のように**ドル表記の直後にカッコ書きで円換算の目安を必ず併記する**(1ドル150円換算などレートを明記し、正式なJPY価格ではなく目安である旨が伝わるようにする)。
  - Why: ユーザーから「価格や販売元も欲しい」「ドル価格の後ろにカッコ書きで円も」と指示があった。
  - How to apply: 着用アイテムのブランド特定記事では、ブランド名の特定だけで終わらせず、価格・販売元セクションを追加する。日本円の正確な価格が確認できない場合は、米ドル価格+カッコ書きの円換算(目安であることが分かる書き方)で代用する。
- **「Xで気づいたファンが特定した投稿が広まりました」のように、ブランド特定という記事の核心部分の手柄をXの投稿者側に譲るような書き方をしない**(2026-08-09にユーザー指示)。「ファンが特定した」と書くと、その特定作業がブログ側のオリジナルな調査ではなく他人の後追いに見えてしまい、記事の独自性が薄れる。
  - Why: 宮近海斗のLevi's×Sky High Farm Tシャツ記事で「背中いっぱいにプリントされた赤いバンダナ柄のボックスロゴにXで気づいたファンが、着用しているTシャツのブランドを特定した投稿が広まりました」という一文について、ユーザーから「ファンが特定したってワードはいらない、ブログのオリジナリティーなくなりそう」と指摘された。
  - How to apply: 着目点(ロゴ・柄など)が話題になった事実は書いてよいが、「Xで話題になっています」のように留め、「特定した」「特定した投稿が広まった」のような手柄をSNS投稿者に帰属させる言い回しは避ける。実際のブランド特定・裏取りはこのブログ側の調査として提示する。
  - **同日追加確認(松倉海斗のクロムハーツ指輪記事)**: 「特定した」という動詞を使っていなくても、「この投稿を見たXユーザーが〜に注目し、〜という商品画像を並べて紹介しました」「Xでは、この投稿を受けて〜の可能性が高いと指摘する投稿があり」のように、**他人の投稿の行為(注目した・紹介した・指摘した)を主語にして経緯を説明する書き方も同じNG**とユーザーから指摘された(「ここいらない」「他人のXの投稿記事のことは不要」)。「松倉さんの指に着けられた複数の指輪に注目が集まりました」で事実だけ触れ、ブランドの結論は「調査の結果、〜の可能性が高いことが分かりました」のように自分たちの調査結果として直接言い切る形にする。画像のfigcaption出典URL明記(著作権上必須)とは別の話で、そちらは引き続き必ず書く。
  - **追加確認(2026-08-12、吉澤閑也の誕生日会場特定記事)**: 「〜という投稿がXにも見つかりました。そこには位置情報として店名が添えられており、それが◯◯でした」のように、**ファンの特定投稿にあった位置情報タグ・店名などの発見過程をそのまま経緯として書く言い回しも同じNG**とユーザーから指摘された(「ここの文はいらない」「ファンの特定の投稿での写真と位置情報だから」)。他人の投稿行為を主語にしていなくても、「その投稿のおかげで店名が分かった」という発見の経緯自体を書くと結局手柄がファン側に見えてしまう。会場名は「調査の結果、会場は◯◯とみられることが分かりました」のように、発見経緯を説明せずいきなり結論から書き、根拠(内装写真の一致など)はブログ側の裏取りとして続ける。
  - **例外: 記事の主題そのものがファン発の創作物・文化(ケミ名などの愛称、二次創作的な呼び方)である場合は、この「手柄を譲らない」ルールは適用しない(2026-08-25、KO1KEYZ「ケミ名」まとめ記事で確認)**。ブランド特定・ロケ地特定のような記事は「このブログが独自に調べて突き止めた」ことが価値なので手柄を譲ると原稿の独自性が薄れるが、「ケミ名」のようなファンダム文化そのものを紹介する記事は、その呼び名を生み出したのがファン(X)であること自体が記事の面白さの核なので、「Xで生まれた呼び方」「ファンの間で広まった愛称」のように出どころをX/ファンに帰属させてよい。むしろ「マツが調べた」のように調査主体(アシスタント側)を主語にする方が不自然。判断の軸は「ブログの調査力を見せたい記事か」「ファンの創作文化そのものを紹介したい記事か」。

## 目撃・遭遇情報の書き方(2026-08-05にユーザー指示)

X上の1件の目撃投稿(写真・動画なしのテキストのみの報告など)を記事で紹介する際、裏付けの弱さを気にしすぎて言い訳めいた一文を重ねない。

- **NG例**: 「この投稿に写真の添付はなく、目撃者本人による文章だけの報告のため、正確な時間帯や場所までは特定できていません。投稿者自身も『時差をつけて投稿している』と補足しており、実際に目撃したタイミングと投稿日時には多少のズレがある可能性があります」「テキストのみの目撃情報は、写真や動画付きの投稿に比べて裏付けが取りづらいのも事実です。出どころが不明な噂の可能性があるため、公式発表や複数の投稿による裏付けがあるかを確認してから受け止めることをおすすめします」のような、目撃情報の信頼性の弱さを何段落にもわたって釈明する書き方。
- **OK**: 「〇〇でメンバーを見かけたというXの投稿が見つかりました」のように、目撃情報があったという事実を淡々と伝えるだけでよい。
- Why: KO1KEYZの仁川空港目撃記事で、渋谷での目撃情報(写真なし・投稿者が「時差をつけて投稿している」と補足)を紹介した際、上記NG例のような裏付けの弱さを何度も強調する文章を書いたところ、「ここの文章はいらない」「投稿者が時差をつけて投稿してるとかの文章もいらないかな、もくげきじょうほうがあったっていう事実だけでいいかな」とユーザーから指摘され、該当箇所を削除した。
- **本人や運営からの公式発表ではない」という留意点そのものは書いてよい**(事実に基づく前提の明示であり、今回NGとされたのは「投稿者が時差をつけて投稿」のような瑣末な裏付けの弱さを重ねて強調する部分)。ただし1文程度に留め、同じ趣旨の注意書きを段落ごとに繰り返さない。
- How to apply: 目撃・遭遇系の記事でSNS投稿を紹介するときは、まず目撃内容そのものを簡潔に書く。裏付けの弱さに触れる場合も最小限(せいぜい1文)に留め、投稿の細かい体裁(時差投稿である旨、写真の有無など)まで逐一言い訳のように書き連ねない。
- 上記の指摘を反映して該当箇所を削除した最終版について、ユーザーから「見やすい!いいね!」と好評だった(2026-08-05)。今後も目撃・遭遇系の記事はこの簡潔な書き方をデフォルトにしてよい。

## SNS投稿を紹介するときは投稿文をそのまま詳しく引用しない(2026-08-06にユーザー指示)

きっかけになった1件のX投稿を本文で紹介するとき、投稿本文をほぼそのまま(投稿時刻・ハッシュタグまで含めて)引用しない。

- **NG例**: 「19時45分ごろに投稿された内容は『AppleWatchユーザーなのめろすぎ』というシンプルなもので、『#TravisJapan』『#シン日本遺産』のハッシュタグとともに広まりました」のように、投稿時刻・ハッシュタグ・文面を逐一書き出す。
- **OK例**: 「今回の放送をリアルタイムで見ていたファンの間で、〇〇が話題になりました」のように、話題になったという事実を簡潔に地の文で伝える。
- 過去投稿を裏付けとして引用する場合も同様で、投稿文の面白おかしい言い回しまで丸ごと引用せず、事実確認に必要な核の部分だけを短く引用する(例:「宮近海斗のApplewatchが16:41をお知らせしてるだけで飲める酒があります」→「宮近海斗のApplewatchが16:41をお知らせしてる」)。
- Why: 宮近海斗のApple Watch記事で、投稿時刻・ハッシュタグまで含めた詳しい引用をしたところ「ここまで投稿文詳しく書かなくていいかな」とユーザーから指摘され、簡潔な言い回しに修正した。
- How to apply: SNS投稿を紹介する記事全般で、まず「話題になった事実」を短い地の文で書き、引用符「」を使う場合も要点だけの短い引用に留める。[SNSの反応まとめセクションの見せ方](#snsの反応まとめセクションの見せ方2026-08-03にユーザー指示)の「引用は短く削る」方針と同じ考え方。

## SNSの反応の引用が2つ以上並ぶ箇所は枠で囲う(2026-08-22にユーザー指示)

「SNSでの反応まとめ」という専用セクションでなくても、メンバー紹介・エピソード紹介など通常の解説セクションの中で根拠となるSNS投稿の引用を2つ以上並べたい場面は多い。これを地の文にそのまま埋め込むと1段落が長くなり読みづらい。

- 地の文では「いつ・どのツアーや番組で・どんな内容だったか」という事実だけを簡潔に書く。
- 引用を2〜3個並べたい場合は、地の文から切り離して専用の軽量box(タイトルバーなし、`border`+背景色のみ)にまとめる。引用は「」で囲んだ短いフレーズだけに絞り、投稿の前後の説明・ハッシュタグ・絵文字は削る。
  ```html
  <!-- wp:html -->
  <div style="border:1px solid {BORDER_LIGHT};border-radius:4px;padding:10px 16px;margin:0 0 16px 0;background:{BG};">
  <p style="margin:0 0 6px 0;font-weight:bold;font-size:0.9em;color:{BORDER};">Xでの反応</p>
  <p style="margin:0;font-size:0.95em;">「引用1」<br>「引用2」<br>「引用3」</p>
  </div>
  <!-- /wp:html -->
  ```
  (色はその記事のアクセントカラー([[docs/rules.mdの本文中の強調・ボックス装飾ルール]]参照)に合わせる。既存の「この記事でわかること」boxと同じインラインstyle方式。)
- これは[SNSの反応まとめセクションの見せ方](#snsの反応まとめセクションの見せ方2026-08-03にユーザー指示)の「カテゴリごとにcapboxで分ける」方針と同じ考え方を、専用の「SNSでの反応」見出しを立てない通常の解説セクションにも広げたもの。
- Why: Travis Japanのカラコン特定記事(chomoand-0.com下書きID879)で、メンバーごとのセクション本文にファンの反応引用を複数埋め込んだところ、「どこの項目もSNSのファンのリアクションコメント入れるのはすごくいいんだけど、それによって文章が長くなって読みづらい」「ファンのリアクションは枠で囲って簡潔に入れるとか工夫が欲しい」と指摘され、地の文(事実)と引用(枠内)を分離する形に修正した。ユーザーから「記事全体のルールにする」と明言され、サイト共通ルールとして確定した。
- How to apply: 新規記事・リライトを問わず、本文中でSNS投稿の引用を2つ以上並べる箇所では、専用の「SNSでの反応」見出しの有無にかかわらず最初からこの枠を使う。引用が1つだけの場合は無理に枠にせず地の文に短く織り込んでよい。

## SNSの反応まとめセクションの見せ方(2026-08-03にユーザー指示)

「SNSでの反応まとめ」のようにXの声を複数まとめて紹介するセクションで、`<strong>カテゴリ名</strong>:「引用1」「引用2」…という説明文` を1個の`<li>`に詰め込む書き方は、行が長くなり過ぎて読みにくい。

- カテゴリ(サイズへの期待・価格への懸念、など)ごとに**独立したSWELLのcapboxブロックに分ける**。1カテゴリ=1つの`swell-block-capbox`とし、`cap_box_ttl`にカテゴリ名、`cap_box_content`内の`<ul>`に短い引用を2〜3個だけ箇条書きにする。
  ```html
  <div class="swell-block-capbox cap_box is-style-small_ttl">
    <div class="cap_box_ttl">サイズへの期待</div>
    <div class="cap_box_content">
      <ul><li>「日本向けにサイズ調整しないでほしい」</li><li>「アルミホイルで巻いた雑な感じが好き」</li></ul>
    </div>
  </div>
  ```
  (STEP1.5のブロック変換ルール通り、この div ごと`<!-- wp:html -->`で囲む)
- **引用文は短く削る**。元のツイートの補足説明(「〜など、〜という声が目立った」)は箱の外の前後の地の文でまとめて説明し、箱の中は「」で囲んだ短い引用だけにする。
- Why: ピンクスホットドッグス×Travis Japan記事で、SNS反応を1つの`<ul>`に4カテゴリ分まとめて長文の`<li>`を並べたところ、ユーザーから「もう少し見やすくしてほしい」と指摘された。カテゴリごとに視覚的に区切られたボックスへ分割し、引用も短くしたところ改善した。
- How to apply: SNS/Xの反応を複数カテゴリに分けて紹介する記事全般(グルメ・ニュース系記事のコメント欄まとめなど)で、最初から1個の`<ul>`に長文`<li>`を詰め込まず、カテゴリ数だけcapboxを並べる構成で書く。

## YouTube動画発記事の情報の選び方(2026-07-30にユーザー指示、最重要)

YouTube動画を情報源に記事を書く際、動画内で語られている内容をそのまま要約するだけの記事は検索需要が無い。

- **人は疑問が湧かないと検索しない**。動画の内容(企画のルール、メンバーが語ったエピソードなど)は動画を見れば分かることなので、それをまとめただけの記事に価値は無い。
- **価値があるのは「動画内で紹介されていない情報」**。具体的には出演者が身につけている服・アクセサリーの詳細、ロケ地(店舗・施設)の特定、その場で食べていたものなど、映像には映っているが動画のナレーション・会話では言及されていない情報。
- **記事の軸足は「動画の内容紹介」ではなく「映像から読み取れる未言及情報」に置く**。動画の要約は結論ファーストの導入で1〜2文に圧縮し、本文の大部分は服装・アクセサリー・ロケ地・食べ物など「見れば映っているが説明されていない」情報の深掘りに使う。
  - Why: Snow Man「佐久間ドッキリ企画」の記事で、当初は動画内で語られた"隠しネタ"の内容をそのままリスト化しただけの記事を書いたところ、ユーザーから「動画で説明している内容に疑問は湧かない、大切なのは紹介されていない情報」と指摘され、私服・アクセサリー・ロケ地・食べ物を軸にした構成へ全面的に書き直した。
  - How to apply: [youtube-talent-monitorツール](tools.md)のtranscript(文字起こし)はあくまで背景把握・文脈確認用に使う。記事本文の主役はvisual_notes(画像解析結果)から得られる服装・アクセサリー・ロケ地の情報にする。着用アイテムを「私物」「私服」と断定しないルール(下記「ファッション・私物特定記事のルール」)も合わせて守ること。

## 内部リンクのアンカーテキストは具体的にする(2026-08-10にユーザー指示)

記事末尾に同一人物の関連記事を複数リンクするとき、`<a href="...">こちらの記事</a>`を複数個並べると、どのリンクが何の記事なのか読者に伝わらず、クリック率が下がる。

- **NG例**: 「松倉海斗の着用アイテムについては<a>こちらの記事</a>や<a>こちらの記事</a>、<a>こちらの記事</a>でも詳しく紹介しています。」のように、同じ「こちらの記事」を複数回使う。
- **OK例**: 「<a>「ONE PIECE BASE SHOP」Tシャツの価格を調査した記事</a>や<a>STARで履いていたスニーカーのブランドを特定した記事</a>、<a>指に着けていたクロムハーツの指輪を調査した記事</a>」のように、リンクごとにそのリンク先が何の記事か(アイテム名・トピック)をアンカーテキストに含める。
- Why: 松倉海斗のBALENCIAGAバックロゴTシャツ記事で「こちらの記事」を3つ並べたところ、「『こちら』だとなんの記事なのかわかりづらくてクリックされないかも」とユーザーから指摘された。
- How to apply: 記事末尾・本文中を問わず、同一記事内に複数の内部リンクを置くときは、アンカーテキストを「こちらの記事」のような汎用文言で使い回さず、リンク先記事の主題(アイテム名・番組名・エピソード名など)を毎回入れる。

### 関連リンクが2件でも枠+箇条書きにしてよい(2026-08-21追加)

上記「関連記事の内部リンクが3件以上並ぶ文章は箱にする」ルールは、実際には2件でも地の文に埋め込むと読みにくいことが分かった。

- How to apply: 内部リンクが2件以上、地の文の1文に複数個詰め込まれそうになったら、件数が3件未満でも最初から箱+箇条書きにする。3件という閾値にこだわらない。

## 内部リンク(サイト内リンク)ルール(2026-07-24にユーザー指示)

特定の人物(KO1KEYZメンバーなど)に関する記事を書く際は、**そのサイト内に既にある同一人物の関連記事(wiki・学歴・家族構成・彼女など)を必ず探し、本文中にリンクを貼る**。

- 対象記事を書く前に`articles/`配下・WordPress側(カテゴリ・タグ・検索)でその人物名を検索し、既存記事の有無を確認する。
- 見つかった記事は、本文の自然な流れの中(冒頭の関連リンクブロック、または関連する話題に触れた箇所)にリンクを設置する。まとめて「関連記事」ブロックとして記事末尾に並べてもよい。
- **この確認・リンク付けは今後そのメンバー(人物)に関する記事を書くたび毎回必ず行う**。1回やって終わりではなく、恒久的なルール。
- 新しく記事を公開したら、その人物についての「今ある関連記事一覧」が1本増えたことになるので、次にその人物の記事を書くときはその増えた記事も対象に含める。

## 本文中に韓国語の固有名詞を出すときは読み方+日本語訳を入れ子カッコで併記する(2026-08-17にユーザー指示)

chomoand-1.com(コイキーズブログ)のJP記事で、施設名・団体名など韓国語のハングル表記をそのまま本文に出す場合、読者が読めない・意味が分からない状態にならないよう直後にカタカナ読み+日本語訳を添える。

- **形式は「ハングル(カタカナ読み(日本語訳))」の入れ子カッコ**。例: `원마운트 스노우파크(ウォンマウントゥ・スノウパク(ワンマウント・スノーパーク))`。当初「読み=訳」のように`=`で区切っていたが、2026-08-17にユーザーから「ウォンマウントゥ・スノウパク(ワンマウント・スノーパーク)でいいかな」と入れ子カッコ形式への修正指示があり、これが確定形。
- **注記を付ける箇所**: そのハングル語句が登場する記事冒頭(リード文)の初出、および各H2見出し(見出し単体で読まれる・目次的にジャンプされる可能性があるため)、見出し直後の本文1文目。同じH2セクション内で2回目以降同じ語句が出てくる場合は毎回付けなくてよい(すでに直前で説明済みのため)。
- Why: KO1KEYZ「KO1WORLD」ロケ地特定記事(chomoand-1.com下書きID11410)で원마운트 스노우파크という韓国語施設名を各所で使ったところ、見出し単体・本文単体でハングルだけが浮いて読めない箇所が複数あり、ユーザーから複数回「ここにカッコ書きで読み・訳がほしい」と指摘された。
- How to apply: 韓国語の固有名詞(施設名・エリア名など)を本文で使う記事を書くときは、最初から上記の入れ子カッコ形式で読み・訳を付けて執筆する。

## 見出しに入れたトピックは本文でも必ず触れる(2026-08-21追加)

H2見出しに入れた話題(例:「アンコールの撮影OKタイム・トロッコ」)のうち、実際には本文でほとんど触れていないものがあると、ユーザーから「ここ、〜のこと全然触れてないよね?」と指摘される。

- 見出しに含めた各トピックについて、最低でも独立した1〜2文は必ず本文に用意する。トピックが複数ある見出し(「A・B・Cはどうだった?」形式)では、それぞれ専用の段落に分けると対応関係が分かりやすい(KO1KEYZファンミDAY1記事で「撮影OKタイム」と「トロッコ」を別々の段落に分離した実例)。
- 逆に、その話題を厚く書く予定がないなら、最初から見出しに入れない。見出しは記事の「目次」として機能するため、見出しと中身が食い違うと読者の期待を裏切る。
- How to apply: 見出しを決める前に、その見出しに含めるトピックそれぞれについて最低1文書けるか自問する。書けない・書く予定がないトピックは見出しから外す。

## 一次情報(現地写真など)が手に入ったらファン予想の図を確定情報に格上げする(2026-08-21追加)

ファンの投稿から作った推測ベースの図(座席ブロックの並び予想など)を使っていた記事に、後から現地の案内板を撮影した写真のような確度の高い一次情報が手に入ることがある。

- KO1KEYZファンミDAY1レポート記事で、ファン共有の座席ブロック画像(伝聞ベース)を使っていたところ、ユーザーから現地の「アリーナ客席図」案内板の実物写真が提供され、「この座席表は参戦者の写真だから確実」「見て図にして載せてほしい」と指示があった。
- 一次情報の写真をそのまま埋め込むのではなく、見やすいよう清書した図として再作成するのが有効(`tools/gen_ko1keyz_fanmi_day1_seatmap.py`でPillowを使い再作図した実例)。文章側も「〜という証言があり」のような伝聞ヘッジから「現地の案内板によると」という確定的な言い回しに格上げする。もともとのファン予想画像・文章(座席番号・列数など、一次情報の写真には無い詳細)は重複しない範囲で残してよいが、同じ内容が両方の画像で表現される場合はファン予想側の画像を削除し、ユニークな数値情報だけ本文に統合する。
- How to apply: 記事作成後にユーザーから「これは確実」「本人が撮った写真」のような一次情報が追加提供されたら、既存のファン予想ベースの図・文章をそのまま残さず、確度が上がったことを前提に図の再作成とヘッジ表現の見直しをセットで行う。

## 記事本文にマツ(アシスタント)を主語にした記述を書かない(2026-08-25追加)

「Xの投稿からマツが見つけられた分を一覧にまとめました」のように、調査主体としてマツ(アシスタント)自身を記事の地の文に登場させない。

- 読者から見れば記事は「このブログが調べた・まとめた」ものであり、誰が(どのAIが)実務を担当したかは記事の内容と無関係。マツという固有名詞を本文に出すと違和感が強い。
- Why: KO1KEYZ「ケミ名」まとめ記事の下書きで「マツが独自に調べて一覧化した」という一文が入っていたところ、ユーザーから「みんな驚く」「マツのことは書かなくていい」と指摘され削除した。
- How to apply: 記事の地の文は「このブログでは」「調べたところ」のような主体をぼかした言い回しか、[手柄をXの投稿者側に譲らない](#ファッション私物特定記事のルール2026-07-29にユーザー指示)ルールの例外に当たる場合は「X上で」「ファンの間で」を主語にする。マツ・アシスタント・AIといった制作側の存在は本文に一切出さない。

## 「一覧・早見表」系記事でファンの編集物をそのまま流用しない(2026-08-25追加)

メンバーの愛称・呼び方・組み合わせなどを網羅的に一覧化する記事(「〇〇まとめ」「〇〇早見表」)を書くとき、Xで見つけたファン手作りの一覧画像(表・相関図など)をそのまま本文に埋め込んで済ませない。

- 表・相関図のような**情報の選定と配置(編集著作物)は、個々の事実と違って作成した本人の創作性が認められる部分**。1枚の画像をまるごと転載するのは、たとえ出典URLを明記していても「その人の編集作業をそのまま拝借した」印象になりやすい。
- **対応策**: ①その画像は情報源の1つとして参考にしつつ、可能なら別の独立した情報源(過去の個別投稿、別のファンが作った一覧、Q&Aサイトの回答など)でも同じ情報が言及されているか確認する。②表形式を流用せず、自分たちの構成(2列の一覧リストなど、元の資料とは違うレイアウト)で書き直す。③複数の情報源で呼び方が食い違う場合は「呼び方は複数ある」こと自体を記事の面白さとして書く。
- Why: KO1KEYZ「ケミ名」まとめ記事で、当初Xで見つけた12人×12人の「ケミ名早見表」画像をそのまま本文に埋め込んでいたところ、ユーザーから「これマツが作り直していれるのはどう?パクリになるの?」と懸念が示された。検討の結果、画像埋め込みをやめ、複数の独立した情報源(その表・別のテキスト形式リスト・Q&Aサイトの回答)を突き合わせて自前の2列一覧表に作り直した。
- **一方で、確認できた情報とできなかった情報を色分け・注記で区別する必要は基本的にない(2026-08-25追加)**。当初「確認済み/情報あり(未確認)」の2段階表示(列・色分け・凡例)を導入したが、ユーザーから段階的に「列いる?」「確認済みは必要?」と指摘され、最終的に全て削除してシンプルな一覧表に落ち着いた。裏取りの厳密さを読者向けの表示に反映させるより、記事の見やすさを優先する。裏取りの経緯そのものは(必要なら)自動メモリ側の作業記録に残せば十分で、記事本文・表に出す情報ではない。
- How to apply: 「〇〇まとめ」「〇〇早見表」系の記事を作るとき、元ネタがファン手作りの1枚の画像・表であれば、まず埋め込みで済ませられないか疑い、複数ソースの突き合わせ+自前レイアウトでの再構成を検討する。確認状況を読者向けに区別表示する凝った仕組みは基本的に不要、まず作ってからユーザーに「これいる?」と聞かれたら素直に削る。
