## REST API

- 投稿: `POST {サイトURL}/wp-json/wp/v2/posts`
- メディアアップロード: `POST {サイトURL}/wp-json/wp/v2/media`
- 更新(公開に変更など): `POST {サイトURL}/wp-json/wp/v2/posts/{記事ID}`
- プラグイン一覧取得: `GET {サイトURL}/wp-json/wp/v2/plugins`
- プラグインのインストール・有効化: `POST {サイトURL}/wp-json/wp/v2/plugins` に `{"slug": "プラグインのslug", "status": "active"}` をJSONで送る(WordPress.orgディレクトリのプラグインならZIPアップロード不要でスラッグ指定だけでインストールできる。2026-07-06、WP Sitemap Page導入時に確認)。ただしプラグインのインストール・有効化自体はサイト設定変更にあたるため、CLAUDE.mdのルール通り必ずユーザーに確認してから実行する。
- 認証方式: Basic認証(`username:アプリパスワード`をUTF-8でBase64エンコードし`Authorization: Basic ...`ヘッダーに設定)
- テーマ: 両サイトともSWELLテーマを使用。同じCSSクラス(`swell-block-capbox`・`swl-marker`・`is-style-dent_box`など)がそのまま使える。

## 運用ルール(絶対厳守)

- **記事(投稿・固定ページ問わず)の削除・ゴミ箱移動は、実行前に必ずユーザーの明示的な許可を得ること(2026-08-02にユーザーから指示、方針変更)。** 何を削除するか(URL・タイトル)を具体的に提示して確認を取り、ユーザーがその場で「削除していい」等と明示的に許可した場合に限りDELETEメソッドや`wp post delete`(またはstatus:trashへの更新)を実行してよい。許可を得ずに独断で削除・ゴミ箱移動はしない。
  - Why: 元々は誤削除防止のため口頭許可があっても削除しない絶対禁止ルールだったが、2026-08-02にユーザー自身が「俺が削除していいと言ったらOK」と明示指示し、都度確認→承認ありなら実行、という運用に変更された。
- 投稿はまず`status: draft`(下書き)で作成し、ユーザーが確認したうえで公開する([publishスキル](../.claude/skills/publish/SKILL.md)参照)。
- **「確認したい」「見れないから一度アップして」は「公開して」ではない。** 下書きが見れないという相談を「publishにすれば見れる」と解釈して勝手に公開しない。「公開して」と明示されない限りstatusはdraftのまま維持し、確認方法(wp-adminにログインしてプレビュー等)を案内する。2026-07-04にこれで一度勝手に公開してしまい、ユーザーから訂正が入った。
- WordPressの設定変更(プラグイン・テーマ・サイト設定など)は必ずユーザーに確認してから行う。
- **既存記事の内容変更(単発の編集・書き換え)は必ずユーザーに確認してから実行する(2026-08-02にユーザーから指示)。** ただし`koikeyz-rewrite`スキル([SKILL.md](../.claude/skills/koikeyz-rewrite/SKILL.md)、既存記事の自動リライト)・`publish`スキル([SKILL.md](../.claude/skills/publish/SKILL.md)、下書き→公開へのstatus更新)など、ユーザーが既に個別に依頼して実行される既存の自動化フローは対象外で、これまで通り確認不要。
- Read/下書き投稿(新規作成)は確認不要で実行してよい。DELETE・記事の単発な内容変更・設定変更は確認が必要。
- **下書き記事の内容を`POST {サイトURL}/wp-json/wp/v2/posts/{id}`で更新するときは、`status`フィールドを必ず明示的に含める(`{"status":"draft", "content":...}`)。** `content`だけ送ってstatusを省略すると、既存の下書きが`publish`(公開)状態にリセットされてしまう事象を2026-07-10に確認した。下書き中の記事を編集する処理では省略せず、常に`status: draft`をペイロードに含めること。
- **ユーザーが「削除していい」等その場で明示的に許可した場合は、実際に削除・ゴミ箱移動を実行してよい(2026-08-02〜、旧ルールから変更)。** マツの独断や「消してよさそう」という推測だけでは削除しない。削除前には対象記事のURL・タイトルなど具体的に何を消すのかユーザーに提示し、明示的な承認を得てから実行すること。過去(〜2026-08-01)は口頭許可でも削除せずタイトルに`【削除】`を付けるだけの運用だったが、これは廃止。
- **複数セッション・複数PCで同じ人物/トピックの記事を並行して書いてしまうことがある。** 新しい出演者・トピックの記事に着手する前に、`GET {サイトURL}/wp-json/wp/v2/posts?search={キーワード}&status=any&context=edit`で下書き・公開済みを問わず既存記事の有無を必ず確認する(公開記事だけを見る無認証検索はdraftを見落とすため`status=any`+Basic認証が必須)。重複下書きを見つけた場合は上記の削除ルールに従い、ユーザーに確認のうえ削除するか、確認が取れるまではタイトルに`【削除】`を付けて目印にする。

### chomoand-0.comのインデックス未登録問題(2026-07-07調査)

GSCで「ページがインデックスに登録されていない(noindexタグ/404/4xx/403)」という警告が出た件を調査した記録。

- **調査手法**: REST API(`?status=trash`や`?status=publish`を`context=edit`で叩く)で投稿・固定ページの件数を確認。各公開URLのHTMLをcurlで取得してmeta robotsタグ・canonical・X-Robots-Tagヘッダー・Googlebot UAでの応答コードを確認。`site:chomoand-0.com`のWeb検索でインデックス実態を確認。
- **判明した事実**:
  - 投稿36件+固定ページ3件、計39件がゴミ箱(trash)ステータスになっていた(2026-06-17〜2026-07-05にかけて複数回に分けて実施された形跡)。これが404警告の主因。ユーザーに確認したところ**復元は不要**とのことで、意図した状態(このまま放置でよい)。
  - 現在の公開記事はわずか5件のみ。各記事にnoindexタグ・403ブロックなどの技術的な問題は無し(正常にインデックス可能な状態)。
  - にもかかわらず`site:chomoand-0.com`は検索結果0件 = サイト全体がGoogleにまだインデックスされていない。
  - サイト自体が新しい(WordPress初期投稿「Hello world!」の作成日が2026-06-11で、開設から1ヶ月未満)。
- **結論**: 技術的なバグではなく、①新規ドメインでまだGoogleの信頼が無い、②公開記事数が少なすぎる、③公開→ゴミ箱移動を短期間で繰り返した履歴がクロール評価に悪影響、の複合要因と推測される。GSCの「インデックス登録をリクエスト」を毎日連打しても改善しない(むしろ逆効果の可能性)。
  - **How to apply**: 同様の「インデックスされない」相談が来たら、まず個別記事のnoindex/403/canonicalを技術チェックしたうえで、ドメインの新しさ・公開記事数・ゴミ箱移動履歴も確認すること。技術的に問題が無ければ「時間と実績が必要な状態」であることをユーザーに伝え、インデックス登録リクエストの連打はやめて記事を継続的に増やすよう案内する。

  - 注意: Instagramはアイキャッチ画像が必須(画像なしの記事は投稿不可)。1枚画像のみ対応で、複数画像のカルーセル投稿は不可。

**How to apply:** 記事公開時のSNS自動投稿について聞かれたら、Instagram/ThreadsはJetpack Social、XはZapier等の外部連携、という切り分けで案内する。実際のセットアップ手順・進捗チェックリストは[docs/sns-auto-post-setup.md](sns-auto-post-setup.md)を参照・更新すること。

## 既知の問題: chomoand-0.comのDNS誤設定(2026-07-30発見)

2026-07-30、SNS自動投稿の作業中にchomoand-0.comへの外部接続が全てSSLハンドシケエラー(`SSL: WRONG_VERSION_NUMBER`)で失敗する事象を発見。Anthropic側のネットワーク経由(WebFetch)でも同じ結果だったため、ローカル環境固有の問題ではなくサーバー/DNS側の問題と判明。

- **原因**: `chomoand-0.com`のDNS Aレコードが誤って`18.204.152.241`(AWS上の無関係なHerokuアプリ、`Server: nginx`+`X-Powered-By: Express`+`heroku-router`のレスポンスが返る)を指していた。本来のWordPress実体は`chomoand.com`・`chomoand-1.com`と同じ`85.131.207.35`で正常に生きていることを、Hostヘッダーを`chomoand-0.com`にして直接そのIPへHTTPSアクセスし確認済み(正常なWordPress REST APIレスポンス、サイト名「ちょものJr.情報局」が返った)。
- **確認手段**: 3ドメインとも同じXserverネームサーバー(`ns1〜5.xserver.jp`)を使っているが、chomoand.com・chomoand-1.comは正しく`85.131.207.35`を指し、chomoand-0.comだけ異なるIPを指していたことをGoogle Public DNS(8.8.8.8)・Cloudflare(1.1.1.1)の両方で確認し、DNS伝播遅延ではなく実際のレコード誤りであると特定した。
- **復旧方法**: Xserverの「サーバーパネル」→DNS設定で、chomoand-0.comのAレコードを`85.131.207.35`に修正する(WordPress本体・記事データは無事なため、DNS修正のみで復旧する見込み)。ドメイン管理系の変更のためユーザー本人が対応する必要がある(マツはXserverの認証情報を持っていない)。

### 訂正・解決(2026-08-06夜、根本原因が判明)

上記までの調査(8/2〜8/6)は全て**トモキの自宅Wi-Fi(zaq.ne.jp、ZAQ/J:COM回線)に繋いだMacから**実施していたが、**そのWi-Fiのルーター自体がDNS問い合わせを横取りしていた**ことが判明した。ユーザーが「Wi-Fiを切ってスマホのモバイル回線に切り替えたらアクセスできた」と報告したことがきっかけ。

- **確認方法**: ルーター(デフォルトゲートウェイ`192.168.40.1`)に直接DNS問い合わせすると誤ったIPが返る一方、**DNS over HTTPS(ポート53を経由しない、`https://cloudflare-dns.com/dns-query`・`https://dns.google/resolve`)で問い合わせると、CloudflareもGoogleも両方とも正しい値`85.131.207.35`(TTL 3600、正常値)を返した**。さらに`curl --resolve chomoand-0.com:443:85.131.207.35 https://chomoand-0.com/wp-json/`で直接アクセスし、HTTP 200・正常なWordPress REST APIレスポンス(サイト名「ちょものJr.情報局」)を確認した。
- **結論**: **Xserver側のDNS修正は実際には機能していた(いつから直っていたかは不明)**。8/2〜8/6にこのMacから「まだ直っていない」と繰り返し確認していたのは、自宅Wi-Fiのルーターが古い誤ったDNS応答をキャッシュ(あるいは意図的にpoisoning)し続け、`@8.8.8.8`や`@ns1.xserver.jp`など問い合わせ先を明示的に指定しても全てルーターに横取りされて誤った値を返されていたための**誤診断**だった。それまでの「flapping」「Xserver側で同期不良」という仮説(上記の8/2・8/5・8/6の記述)は誤りだった可能性が高い。
- **対応**: 自宅Wi-Fiルーターの再起動(電源抜き差し)でキャッシュクリアを推奨。それでも直らない場合はルーターのDNS設定を確認、またはISP(ZAQ/J:COM)に問い合わせ。Xserverサポートへの問い合わせについては、既に解決している可能性が高い旨を追って報告し、クローズしてよいか確認すること。
- **How to apply**: 今後、特定のドメインだけ繋がらない相談で`dig`の結果を信用する前に、**同じネットワークのルーターがDNSを横取りしていないか**を先に疑うこと。切り分け方法は「`curl -H "accept: application/dns-json" https://cloudflare-dns.com/dns-query?name={ドメイン}&type=A`(DNS over HTTPSで、通常のポート53を経由しないため大半のルーターの横取りを回避できる)」の結果と、通常の`dig`の結果を比較すること。両者が食い違う場合は、ローカルネットワーク(ルーター/ISP)側の問題であり、リモートサーバー側の設定を疑う前にルーター再起動を試すこと。

**追記: ルーター再起動では直らなかった(2026-08-06夜)**。再起動後も`192.168.40.1`(ルーター)・`@8.8.8.8`・`@1.1.1.1`(いずれも通常のUDP:53)を明示的に指定しても誤ったIPが返り続けた一方、DoH(HTTPS経由)は正しい値を返し続けた。これは**ホームルーター単体のキャッシュではなく、契約プロバイダ(zaq.ne.jp、ZAQ/J:COM回線)のネットワーク側でポート53のDNS通信自体を横取り(トランスペアレントDNSプロキシ)し、そこに古い/誤ったキャッシュが残っている**ためと判断した。ルーター再起動やDNSサーバーの指定変更では解決できない、ISP側の問題。
- **恒久対応の候補**: ISP(ZAQ/J:COM)へ問い合わせるか、自然にISP側のキャッシュが更新されるのを待つ必要がある。マツやユーザー側の設定変更では直接解決できない。
- **当面の回避策**: 該当PCの`/etc/hosts`(Windowsは`C:\Windows\System32\drivers\etc\hosts`)に`85.131.207.35 chomoand-0.com`・`85.131.207.35 www.chomoand-0.com`を追記すれば、DNSに関係なく直接正しいIPへアクセスできる。ISP側の問題が解消されたら忘れずに削除すること。
- **How to apply(追加)**: DoHと通常DNSの結果が食い違い、かつルーター再起動後も直らない場合は、ホームルーターではなくISP側のDNS横取り・キャッシュ問題を疑うこと。この場合の恒久対応はユーザー側では完結せず、ISPへの問い合わせが必要になる(hostsファイルは対症療法にとどまる)。
